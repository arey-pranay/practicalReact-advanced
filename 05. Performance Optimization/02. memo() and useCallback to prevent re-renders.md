# React Performance: `memo()`, `useCallback()`, `useMemo()` & Re-renders

## 1. Why Do Components Re-render?

Before learning optimization, understand the actual problem.

A re-render is not automatically bad. React is designed to render components frequently when state or props change.

The problem occurs when rendering is unnecessarily expensive or causes a large subtree to perform work that it does not need.

# 2. What Causes a React Re-render?

A component can render again when:

1. Its own state changes.

2. Its parent renders again.

3. A context value it consumes changes.

4. An external store it subscribes to updates.

5. Its key changes, causing it to be remounted instead.

### Example

JavaScript

```
function App() {
  const [count, setCount] = useState(0);

  return (
    <>
      <button onClick={() => setCount(count + 1)}>
        {count}
      </button>

      <Child />
    </>
  );
}

function Child() {
  console.log("Child rendered");

  return <p>Child</p>;
}
```

When `count` changes:

```
App state changes
      ↓
App renders again
      ↓
App calls Child()
      ↓
Child renders again
```

Even though `Child` does not receive any changing props, it is rendered because its parent rendered.

# 3. Re-render vs DOM Update vs Remount

These are different concepts.

|
Concept

|

Meaning

|
| --- | --- |
|

Re-render

|

React executes the component function again

|
|

DOM update

|

React commits necessary changes to the DOM

|
|

Remount

|

React removes the previous component instance and creates a new one

|
|

Reconciliation

|

React compares the new render output with the previous tree

|

### Important

A re-render does not necessarily mean the DOM changes.

JavaScript

```
function Child() {
  return <p>Hello</p>;
}
```

The component can execute again, but React may determine that the resulting DOM is unchanged.

```
Parent renders
      ↓
Child function executes
      ↓
React compares output
      ↓
No DOM update required
```

Therefore, the objective of optimization is not simply:

> Prevent every render.

The objective is:

> Avoid unnecessary expensive work when it provides a measurable benefit.

# 4. The Core Problem: Referential Equality

JavaScript compares primitive values and objects differently.

## Primitive values

JavaScript

```
const a = 10;
const b = 10;

console.log(a === b); // true
```

JavaScript

```
const a = "hello";
const b = "hello";

console.log(a === b); // true
```

## Objects

JavaScript

```
const a = { name: "Pranay" };
const b = { name: "Pranay" };

console.log(a === b); // false
```

Although the contents are identical, these are two different object references.

```
a ──────► Object A

b ──────► Object B

Object A !== Object B
```

## Same reference

JavaScript

```
const user = { name: "Pranay" };

const a = user;
const b = user;

console.log(a === b); // true
```

Both variables point to the same object.

# 5. What Is Referential Integrity?

In React performance discussions, the more precise term is usually referential stability or referential equality.

A value is referentially stable when its reference remains the same across renders.

JavaScript

```
const user = useMemo(
  () => ({ name: "Pranay" }),
  [],
);
```

The object reference is preserved between renders unless its dependencies change.

Without memoization:

JavaScript

```
const user = { name: "Pranay" };
```

A new object is created every time the component renders.

### Why does this matter?

React's `memo()` uses shallow prop comparison by default.

```
Previous prop reference === New prop reference?
```

For objects, arrays, and functions, a newly created reference is considered different even if the contents are identical.

# 6. `React.memo()`

`memo()` allows a component to skip re-rendering when its props have not changed according to the comparison React uses.

JavaScript

```
import { memo } from "react";

const Child = memo(function Child({ name }) {
  console.log("Child rendered");

  return <p>{name}</p>;
});
```

Now:

JavaScript

```
function App() {
  const [count, setCount] = useState(0);

  return (
    <>
      <button onClick={() => setCount(count + 1)}>
        {count}
      </button>

      <Child name="Pranay" />
    </>
  );
}
```

When `count` changes:

```
App renders
      ↓
Child receives same primitive prop "Pranay"
      ↓
memo() compares props
      ↓
Child can skip rendering
```

### Without `memo()`

```
Parent renders
      ↓
Child renders
```

### With `memo()`

```
Parent renders
      ↓
Props unchanged?
      │
     Yes
      ↓
Skip Child render
```

`memo()` is a performance optimization, not a guarantee that React will never render the component.

# 7. How Does `memo()` Compare Props?

By default, `memo()` compares each prop using `Object.is()`.

JavaScript

```
const Child = memo(ChildComponent);
```

Conceptually:

JavaScript

```
Object.is(previousProps.name, nextProps.name);
```

For multiple props:

JavaScript

```
const Child = memo(function Child({
  name,
  age,
  user,
}) {
  return <p>{name}</p>;
});
```

React compares the prop values individually.

|
Prop type

|

Example

|

Comparison

|
| --- | --- | --- |
|

String

|

`"Pranay"`

|

Value equality

|
|

Number

|

`10`

|

Value equality

|
|

Boolean

|

`true`

|

Value equality

|
|

Object

|

`{ id: 1 }`

|

Reference equality

|
|

Array

|

`[1, 2]`

|

Reference equality

|
|

Function

|

`() => {}`

|

Reference equality

|

### Important

`memo()` does not perform a deep comparison of objects.

JavaScript

```
{ id: 1 } !== { id: 1 }
```

# 8. Why `memo()` Alone May Not Work

Consider this example:

JavaScript

```
const Child = memo(function Child({ user }) {
  console.log("Child rendered");

  return <p>{user.name}</p>;
});

function App() {
  const [count, setCount] = useState(0);

  const user = {
    name: "Pranay",
  };

  return (
    <>
      <button onClick={() => setCount(count + 1)}>
        {count}
      </button>

      <Child user={user} />
    </>
  );
}
```

Every time `App` renders:

```
App renders
      ↓
New user object created
      ↓
Previous user !== new user
      ↓
memo() detects changed prop
      ↓
Child renders
```

Even though the object has the same content, its reference is different.

# 9. `useMemo()`

`useMemo()` caches the result of a calculation between renders.

JavaScript

```
const value = useMemo(
  () => calculateSomething(a, b),
  [a, b],
);
```

React recalculates the value when one of the dependencies changes.

### Example

JavaScript

```
const user = useMemo(
  () => ({
    name: "Pranay",
  }),
  [],
);
```

Now the same object reference is reused across renders.

JavaScript

```
const Child = memo(function Child({ user }) {
  console.log("Child rendered");

  return <p>{user.name}</p>;
});

function App() {
  const [count, setCount] = useState(0);

  const user = useMemo(
    () => ({ name: "Pranay" }),
    [],
  );

  return (
    <>
      <button onClick={() => setCount(count + 1)}>
        {count}
      </button>

      <Child user={user} />
    </>
  );
}
```

### Render flow

```
App renders
      ↓
useMemo returns same user reference
      ↓
Child receives same prop reference
      ↓
memo() skips Child
```

### Critical relationship

```
memo()  → skips a component when props are unchanged

useMemo() → preserves a calculated value/reference
```

They are often used together when passing objects, arrays, or calculated values to memoized children.

# 10. `useCallback()`

`useCallback()` caches a function reference.

JavaScript

```
const handleClick = useCallback(() => {
  console.log("Clicked");
}, []);
```

It is conceptually similar to:

JavaScript

```
const handleClick = useMemo(
  () => () => {
    console.log("Clicked");
  },
  [],
);
```

The practical API is clearer with `useCallback()` when you want to memoize a function.

# 11. Why Functions Cause Re-renders

JavaScript

```
const Child = memo(function Child({ onClick }) {
  console.log("Child rendered");

  return <button onClick={onClick}>Click</button>;
});

function App() {
  const [count, setCount] = useState(0);

  const handleClick = () => {
    console.log("Clicked");
  };

  return (
    <>
      <button onClick={() => setCount(count + 1)}>
        {count}
      </button>

      <Child onClick={handleClick} />
    </>
  );
}
```

Every render creates a new function:

```
Render 1 → handleClick reference A
Render 2 → handleClick reference B
Render 3 → handleClick reference C
```

Therefore:

```
Previous handleClick !== new handleClick
      ↓
memo() sees changed prop
      ↓
Child renders again
```

# 12. Fixing Function Reference With `useCallback()`

JavaScript

```
const Child = memo(function Child({ onClick }) {
  console.log("Child rendered");

  return <button onClick={onClick}>Click</button>;
});

function App() {
  const [count, setCount] = useState(0);

  const handleClick = useCallback(() => {
    console.log("Clicked");
  }, []);

  return (
    <>
      <button onClick={() => setCount(count + 1)}>
        {count}
      </button>

      <Child onClick={handleClick} />
    </>
  );
}
```

Now:

```
Render 1 → handleClick reference A
Render 2 → handleClick reference A
Render 3 → handleClick reference A
```

Because the function reference remains stable, `memo()` can skip the child when its other props are unchanged.

# 13. `useCallback()` Dependencies and Closures

Consider:

JavaScript

```
const handleClick = useCallback(() => {
  console.log(count);
}, []);
```

This function captures the `count` value from the render in which it was created.

If `count` changes, the callback still references the old value.

This is a stale closure problem.

## Correct dependency

JavaScript

```
const handleClick = useCallback(() => {
  console.log(count);
}, [count]);
```

Now the callback is recreated when `count` changes.

### Trade-off

```
Dependency changes
      ↓
New callback reference
      ↓
Memoized child receiving callback may render
```

This is correct behavior if the callback needs the latest `count`.

# 14. Functional Updates Can Reduce Dependencies

Instead of:

JavaScript

```
const increment = useCallback(() => {
  setCount(count + 1);
}, [count]);
```

Use:

JavaScript

```
const increment = useCallback(() => {
  setCount((prev) => prev + 1);
}, []);
```

The functional state update receives the latest state, so the callback does not need to capture `count`.

This can preserve a stable callback reference.

### Important

Do not remove dependencies merely to make a function stable. Use functional updates when they correctly represent the intended state transition.

# 15. `useMemo()` vs `useCallback()`

|
Feature

|

`useMemo()`

|

`useCallback()`

|
| --- | --- | --- |
|

Caches

|

A calculated value

|

A function reference

|
|

Returns

|

Result of the callback

|

The callback function

|
|

Common use

|

Expensive calculations, stable objects/arrays

|

Stable event handlers/callback props

|
|

Example

|

`useMemo(() => filter(items), [items])`

|

`useCallback(() => save(id), [id])`

|

### Example

JavaScript

```
const filteredItems = useMemo(() => {
  return items.filter((item) => item.active);
}, [items]);

const handleSave = useCallback(() => {
  saveItem(id);
}, [id]);
```

# 16. `useMemo()` for Expensive Calculations

JavaScript

```
const filteredProducts = useMemo(() => {
  return products
    .filter((product) => product.category === category)
    .sort((a, b) => a.price - b.price);
}, [products, category]);
```

Without `useMemo()`:

```
Every render
      ↓
Filter products
      ↓
Sort products
```

With `useMemo()`:

```
Render
  ↓
Did products or category change?
  ├── Yes → Recalculate
  └── No  → Reuse cached result
```

### Do not memoize every calculation

For a tiny calculation:

JavaScript

```
const fullName = `${firstName} ${lastName}`;
```

`useMemo()` adds complexity and has its own bookkeeping cost.

Use it when:

* The calculation is expensive.

* The calculation happens frequently.

* Dependencies often remain unchanged.

* Profiling suggests the calculation is worth optimizing.

* You need a stable object or array reference for a memoized child.

# 17. Memoizing Objects and Arrays

This pattern is common:

JavaScript

```
const filters = useMemo(
  () => ({
    category,
    sortBy,
  }),
  [category, sortBy],
);
```

Then:

JavaScript

```
<Products filters={filters} />
```

If `Products` is memoized:

JavaScript

```
const Products = memo(function Products({
  filters,
}) {
  // ...
});
```

The component can skip rendering when `category` and `sortBy` have not changed.

### Without `useMemo()`

JavaScript

```
const filters = {
  category,
  sortBy,
};
```

A new object is created on every parent render.

# 18. Custom `memo()` Comparator

You can provide a custom comparison function:

JavaScript

```
const UserCard = memo(
  function UserCard({ user }) {
    return <p>{user.name}</p>;
  },
  arePropsEqual,
);
```

The comparator receives:

JavaScript

```
function arePropsEqual(
  previousProps,
  nextProps,
) {
  return true;
}
```

### Return value

|
Return value

|

Meaning

|
| --- | --- |
|

`true`

|

Props are considered equal; React can skip rendering

|
|

`false`

|

Props are considered different; React may render

|

Example:

JavaScript

```
const UserCard = memo(
  function UserCard({ user }) {
    console.log("UserCard rendered");

    return <p>{user.name}</p>;
  },
  (prevProps, nextProps) => {
    return (
      prevProps.user.id === nextProps.user.id &&
      prevProps.user.name === nextProps.user.name
    );
  },
);
```

This comparator compares selected properties rather than the object reference.

# 19. The Most Important Comparator Rule

Your comparator must compare every prop that affects the component's output or behavior.

Bad example:

JavaScript

```
const Button = memo(
  function Button({ label, onClick }) {
    return (
      <button onClick={onClick}>
        {label}
      </button>
    );
  },
  (prev, next) => {
    return prev.label === next.label;
  },
);
```

The comparator ignores `onClick`.

If `onClick` changes, the component might retain an old callback reference.

This can cause stale behavior.

### Better

JavaScript

```
const Button = memo(
  function Button({ label, onClick }) {
    return (
      <button onClick={onClick}>
        {label}
      </button>
    );
  },
  (prev, next) => {
    return (
      prev.label === next.label &&
      prev.onClick === next.onClick
    );
  },
);
```

### Important

A custom comparator is not a replacement for correct state and prop design.

# 20. Why Deep Comparisons Can Be Dangerous

You might be tempted to do this:

JavaScript

```
JSON.stringify(prev) === JSON.stringify(next);
```

Or:

JavaScript

```
deepEqual(prev, next);
```

Potential problems:

* Deep comparison can be expensive.

* Large nested objects increase comparison cost.

* It can be slower than simply rendering the component.

* It may hide poor prop design.

* Some values are difficult to compare correctly.

### Prefer

1. Passing only the props the child needs.

2. Keeping references stable when appropriate.

3. Using primitive props when practical.

4. Using a custom comparator only when profiling supports it.

# 21. Better Prop Design: Pass Primitives

Instead of:

JavaScript

```
<UserCard user={user} />
```

You could pass:

JavaScript

```
<UserCard
  id={user.id}
  name={user.name}
/>
```

Now `UserCard` receives primitive values.

JavaScript

```
const UserCard = memo(function UserCard({
  id,
  name,
}) {
  return (
    <p>
      {id}: {name}
    </p>
  );
});
```

This can make memoization more predictable and reduce unnecessary object-reference changes.

However, passing an object is not inherently bad. Choose the API that makes the component clear and maintainable.

# 22. `memo()` Does Not Stop All Re-renders

A memoized component can still render when:

### Its own state changes

JavaScript

```
const Child = memo(function Child() {
  const [count, setCount] = useState(0);

  return (
    <button onClick={() => setCount(count + 1)}>
      {count}
    </button>
  );
});
```

Its own state update causes it to render regardless of whether its parent props changed.

### A consumed context changes

JavaScript

```
const Child = memo(function Child() {
  const theme = useContext(ThemeContext);

  return <p>{theme}</p>;
});
```

When the relevant context value changes, `Child` can render again.

### A subscribed external store changes

A component using an external store subscription can render when the selected subscribed data changes.

### The parent passes a new prop

Even with `memo()`, new object and function references can cause rendering.
