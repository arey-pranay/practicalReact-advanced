# TypeScript — Part 1

TypeScript is **JavaScript with a static type system**.

It lets us describe what kind of values our code expects so that mistakes can be caught while developing rather than after the application runs.

For React, TypeScript is especially useful for defining:

- component props
- `children`
- callbacks
- state
- DOM events
- component variants
- reusable component APIs

The important thing is not to memorize TypeScript syntax.

The real skill is:

> **Look at a piece of JavaScript and figure out the contract of the values flowing through it.**

---

# 1. What TypeScript Actually Does

Consider JavaScript:

```js
function add(a, b) {
  return a + b;
}

add(10, "20");
```

JavaScript allows this because types are determined at runtime.

With TypeScript:

```ts
function add(a: number, b: number): number {
  return a + b;
}
```

Now:

```ts
add(10, 20);     // ✅
add(10, "20");   // ❌
```

Think of the process as:

```text
TypeScript code
      ↓
Type checking
      ↓
JavaScript
      ↓
Browser / Node.js
```

TypeScript doesn't replace JavaScript at runtime.

The types primarily help **before runtime**.

---

# 2. Basic Types

```ts
let name: string = "Pranay";
let age: number = 22;
let active: boolean = true;
```

Arrays:

```ts
let numbers: number[] = [1, 2, 3];

let names: string[] = ["A", "B", "C"];
```

Objects:

```ts
type User = {
  name: string;
  age: number;
};

const user: User = {
  name: "Pranay",
  age: 22,
};
```

---

# 3. Type Inference

TypeScript doesn't require us to annotate everything.

```ts
const name = "Pranay";
const age = 22;
```

TypeScript infers:

```text
name → string
age  → number
```

So don't unnecessarily write:

```ts
const name: string = "Pranay";
```

when the type is already obvious.

### Rule

> **Explicitly type contracts; let TypeScript infer obvious local values.**

Props are a contract.

Function parameters are a contract.

API boundaries are a contract.

A simple local variable usually doesn't need an annotation.

---

# 4. TypeScript via IntelliSense

This is one of the biggest practical benefits of TypeScript.

Suppose we define:

```ts
type User = {
  name: string;
  age: number;
  email: string;
};

const user: User = {
  name: "Pranay",
  age: 22,
  email: "test@example.com",
};
```

Now type:

```ts
user.
```

Your editor knows that the available properties are:

```text
name
age
email
```

And:

```ts
user.name
```

is known to be a `string`.

So IntelliSense can provide:

- autocomplete
- property suggestions
- parameter information
- function signatures
- error highlighting
- refactoring support
- jump-to-definition

### Why does this work?

Because TypeScript knows the **shape of the data**.

```text
User
 │
 ├── name: string
 ├── age: number
 └── email: string
```

Without that information, the editor has much less to work with.

### React example

```ts
type ButtonProps = {
  label: string;
  disabled?: boolean;
  variant: "primary" | "secondary";
};
```

When using:

```tsx
<Button
  label="Save"
  variant=""
/>
```

your editor can suggest:

```text
primary
secondary
```

This is one reason TypeScript becomes extremely valuable in large React codebases.

# 5. `type` and `interface`

Both can describe object shapes.

```ts
type User = {
  name: string;
  age: number;
};
```

or:

```ts
interface User {
  name: string;
  age: number;
}
```

For the concepts in this README, the important thing is understanding **what the type describes**.

For example:

```ts
type CardProps = {
  title: string;
};
```

means:

> A `Card` expects an object containing a required `title` string.

---

# 6. Define Type of Props

React props are just an object.

Given:

```tsx
<Card
  title="Hello"
  count={10}
/>
```

conceptually the component receives:

```ts
{
  title: "Hello",
  count: 10
}
```

So we can define:

```ts
type CardProps = {
  title: string;
  count: number;
};
```

Then:

```tsx
function Card({ title, count }: CardProps) {
  return (
    <div>
      <h2>{title}</h2>
      <span>{count}</span>
    </div>
  );
}
```

Now TypeScript knows exactly what the component accepts.

---

# 7. Why Type Props?

Without types:

```tsx
function Card({ title, count }) {
  ...
}
```

we don't have a clear contract.

Someone might write:

```tsx
<Card
  title={123}
  count="hello"
/>
```

With:

```ts
type CardProps = {
  title: string;
  count: number;
};
```

TypeScript catches the mistake.

### Mental model

```text
Component
    ↓
has an API
    ↓
Props define that API
    ↓
TypeScript describes the API
```

Props typing is therefore not just about avoiding errors.

It makes the component's **expected usage explicit**.

# 8. Migrating From JavaScript to TypeScript

A very useful way to learn TypeScript is to take an existing JS component and ask:

> **What does this component actually expect?**

Start with:

```jsx
function Button({ label, disabled, onClick }) {
  return (
    <button
      disabled={disabled}
      onClick={onClick}
    >
      {label}
    </button>
  );
}
```

Don't immediately start adding random types.

First inspect the values.

```text
label
  ↓
displayed as text
  ↓
string

disabled
  ↓
button disabled attribute
  ↓
boolean

onClick
  ↓
called as an event handler
  ↓
function
```

Then create the contract:

```ts
type ButtonProps = {
  label: string;
  disabled: boolean;
  onClick: () => void;
};
```

Then migrate:

```tsx
function Button({
  label,
  disabled,
  onClick,
}: ButtonProps) {
  return (
    <button
      disabled={disabled}
      onClick={onClick}
    >
      {label}
    </button>
  );
}
```

### The migration process

```text
JavaScript component
        ↓
Identify inputs
        ↓
Identify their types
        ↓
Identify optional values
        ↓
Identify relationships between values
        ↓
Create Props type
        ↓
Add type annotations
```

This is much better than thinking:

> "How do I convert this JS file to TS?"

Think:

> **"What is the contract of this component?"**

---

# 9. Optional Props

A property followed by `?` is optional.

```ts
type CardProps = {
  title: string;
  description?: string;
};
```

Now both are valid:

```tsx
<Card title="Hello" />
```

and:

```tsx
<Card
  title="Hello"
  description="World"
/>
```

Conceptually:

```ts
description?: string
```

means the value may be:

```text
string
   or
undefined
```

---

# 10. Requiring Props

This is the opposite.

```ts
type CardProps = {
  title: string;
  description: string;
};
```

Both are required.

Therefore:

```tsx
<Card
  title="Hello"
  description="World"
/>
```

is valid.

But:

```tsx
<Card title="Hello" />
```

is an error.

### Important

Don't make props optional simply because it makes TypeScript errors disappear.

Ask:

> **Does this component actually need this value?**

If yes:

```ts
title: string
```

If no:

```ts
title?: string
```

### Mental model

```text
title: string
      ↓
must exist

title?: string
       ↓
may not exist
```

---

# 11. PropTypes in JavaScript

Before TypeScript, React applications commonly used **PropTypes**.

```jsx
import PropTypes from "prop-types";

function Button({ label, size }) {
  return <button>{label}</button>;
}

Button.propTypes = {
  label: PropTypes.string.isRequired,
  size: PropTypes.oneOf([
    "small",
    "medium",
    "large",
  ]),
};
```

PropTypes provide **runtime validation**.

TypeScript provides **static/compile-time checking**.

| | PropTypes | TypeScript |
|---|---|---|
| Language | JavaScript | TypeScript |
| Checking | Runtime | Compile/editor time |
| IntelliSense | Limited | Strong |
| Detects errors before running | ❌ | ✅ |
| Runtime validation | ✅ | ❌ by itself |

So:

```text
PropTypes
   ↓
"Did this component receive valid props at runtime?"

TypeScript
   ↓
"Is this code using the component correctly?"
```

If a project is already TypeScript-based, ordinary prop typing generally doesn't need PropTypes as well.

# 12. Defining Types for `children`

Consider:

```tsx
<Card>
  <h2>Hello</h2>
</Card>
```

The content inside `<Card>` becomes the `children` prop.

Conceptually:

```ts
{
  children: ...
}
```

So:

```ts
type CardProps = {
  children: React.ReactNode;
};
```

Then:

```tsx
function Card({ children }: CardProps) {
  return (
    <div className="card">
      {children}
    </div>
  );
}
```

---

# 13. What Is `ReactNode`?

`React.ReactNode` represents content that React can render.

Examples:

```tsx
"Hello"
```

```tsx
123
```

```tsx
<div>Hello</div>
```

```tsx
<>
  <A />
  <B />
</>
```

and conditional content:

```tsx
{condition && <Something />}
```

Therefore:

```ts
children: React.ReactNode;
```

means:

> This component accepts general React-renderable content.

For general-purpose `children`, this is usually the type you want.

---

# 14. `JSX.Element`

A `React.JSX.Element` represents a React element produced by JSX.

For example:

```ts
const element: React.JSX.Element = (
  <div>Hello</div>
);
```

Conceptually:

```text
ReactNode
    │
    ├── React element
    ├── string
    ├── number
    ├── null
    ├── boolean
    └── arrays / other renderable nodes
```

while:

```text
React.JSX.Element
       ↓
a React element
```

So don't automatically use `JSX.Element` for every React value.

---

# 15. `JSX.Element` vs Array vs `ReactNode`

This distinction is important.

### One element

```ts
React.JSX.Element
```

Example:

```tsx
<div>Hello</div>
```

---

### Array of elements

```ts
React.JSX.Element[]
```

Example:

```tsx
[
  <div>A</div>,
  <div>B</div>,
]
```

This specifically describes an array whose items are React elements.

---

### General renderable content

```ts
React.ReactNode
```

This is broader.

```text
React.JSX.Element
       ↓
one element

React.JSX.Element[]
       ↓
array of elements

React.ReactNode
       ↓
general React-renderable content
```

So for:

```ts
type CardProps = {
  children: React.ReactNode;
};
```

we are saying:

> `Card` doesn't care whether its children are one element, several elements, text, numbers, conditional content, etc.

---

# 16. `PropsWithChildren`

Instead of manually writing:

```ts
type CardProps = {
  title: string;
  children?: React.ReactNode;
};
```

React provides:

```ts
React.PropsWithChildren<CardProps>
```

For example:

```ts
type CardProps = {
  title: string;
};

function Card({
  title,
  children,
}: React.PropsWithChildren<CardProps>) {
  return (
    <div>
      <h2>{title}</h2>
      {children}
    </div>
  );
}
```

Conceptually:

```text
CardProps
   +
children?: ReactNode
   ↓
PropsWithChildren<CardProps>
```

So:

```ts
React.PropsWithChildren<CardProps>
```

is essentially a convenient way of saying:

```ts
CardProps & {
  children?: React.ReactNode;
}
```

# 17. Extending Props with Helpers

A common problem is that your custom component wraps a native HTML element.

For example:

```tsx
<Button
  label="Save"
  disabled
  type="submit"
  onClick={handleClick}
/>
```

We don't want to manually define every native button property.

Instead:

```ts
type ButtonProps =
  React.ComponentProps<"button"> & {
    label: string;
  };
```

Now `ButtonProps` contains the normal `<button>` props plus our custom `label`.

### Mental model

```text
React.ComponentProps<"button">
          ↓
native button props

       +

{ label: string }
       ↓
custom Button props
```

This is an example of **reusing an existing type instead of recreating it**.

---

# 18. Intersection Types — `&`

The `&` operator combines types.

```ts
type User = {
  name: string;
};

type Timestamp = {
  createdAt: Date;
};

type UserWithTimestamp =
  User & Timestamp;
```

The resulting type requires both:

```ts
const user: UserWithTimestamp = {
  name: "Pranay",
  createdAt: new Date(),
};
```

Think:

```text
User
{name}

   +

Timestamp
{createdAt}

   ↓

{name, createdAt}
```

This is particularly useful for extending React props.

---

# 19. Props with Variant Types

Suppose we have:

```tsx
<Button variant="primary" />
<Button variant="secondary" />
<Button variant="danger" />
```

We could write:

```ts
type ButtonProps = {
  variant: string;
};
```

But that's too loose.

It allows:

```tsx
<Button variant="banana" />
```

Instead:

```ts
type ButtonProps = {
  variant:
    | "primary"
    | "secondary"
    | "danger";
};
```

Now TypeScript knows the exact allowed values.

This also improves IntelliSense:

```text
variant:
  primary
  secondary
  danger
```

---

# 20. Differentiating Props

Sometimes different variants don't merely have different values.

They require **different props**.

For example:

```tsx
<Button
  variant="link"
  href="/home"
/>
```

versus:

```tsx
<Button
  variant="button"
  onClick={handleClick}
/>
```

We can model this with a discriminated union:

```ts
type LinkButtonProps = {
  variant: "link";
  href: string;
};

type NormalButtonProps = {
  variant: "button";
  onClick: () => void;
};

type ButtonProps =
  | LinkButtonProps
  | NormalButtonProps;
```

Now TypeScript understands the relationship:

```text
variant = "link"
       ↓
href required

variant = "button"
       ↓
onClick required
```

So this becomes invalid:

```tsx
<Button
  variant="link"
  onClick={handleClick}
/>
```

because a link variant expects `href`.

---

# 21. Why Differentiating Props Is Useful

Consider the weaker version:

```ts
type ButtonProps = {
  variant: "link" | "button";
  href?: string;
  onClick?: () => void;
};
```

This allows nonsense such as:

```tsx
<Button
  variant="link"
  onClick={handleClick}
/>
```

or:

```tsx
<Button
  variant="button"
  href="/home"
/>
```

The type doesn't understand the relationship.

The discriminated union does:

```text
             variant
                │
       ┌────────┴────────┐
       ↓                 ↓
    "link"             "button"
       │                 │
       ↓                 ↓
     href             onClick
```

This is one of the most useful advanced patterns for designing React component APIs.

# 22. Empty Object as a Type

This is an important TypeScript gotcha.

You might see:

```ts
type Props = {};
```

and assume:

> "This means this component accepts no props."

That's **not what `{}` means in TypeScript**.

It does not mean:

```text
an object containing zero properties
```

Instead, `{}` is a broad non-nullish type.

Therefore, don't use:

```ts
type Props = {};
```

as your general way of saying "no props".

---

# 23. A Component With No Props

If a component doesn't need props:

```tsx
function Logo() {
  return <div>Logo</div>;
}
```

That's perfectly fine.

You don't need:

```ts
type LogoProps = {};
```

If you genuinely need a type that only accepts an object with no properties, one option is:

```ts
type EmptyProps = Record<string, never>;
```

Now:

```ts
const props: EmptyProps = {};
```

works, while:

```ts
const props: EmptyProps = {
  name: "Pranay",
};
```

doesn't.

### Remember

```text
{} 
≠
"object with zero properties"
```

This is a classic TypeScript gotcha.

# 24. A Complete React Example

Let's combine the topics.

```tsx
type CardProps = {
  title: string;
  variant: "default" | "featured";
};

function Card({
  title,
  variant,
  children,
}: React.PropsWithChildren<CardProps>) {
  return (
    <article className={`card ${variant}`}>
      <h2>{title}</h2>

      {children}
    </article>
  );
}
```

Usage:

```tsx
<Card
  title="TypeScript"
  variant="featured"
>
  <p>Learning TypeScript.</p>
  <button>Continue</button>
</Card>
```

Here:

```text
title
  → required string

variant
  → required union

children
  → optional ReactNode
```

# 25. The TypeScript Thinking Process

When you encounter an untyped React component, don't immediately think about syntax.

Use this process:

```text
                 React Component
                       │
                       ↓
                 What enters it?
                       │
                       ↓
                     Props
                       │
          ┌────────────┼────────────┐
          ↓            ↓            ↓
        value       callback     children
          │            │            │
          ↓            ↓            ↓
        type         function    ReactNode
```

Then ask:

### Is it required?

```ts
title: string
```

or:

```ts
title?: string
```

### Does it have fixed allowed values?

```ts
variant: "primary" | "secondary"
```

### Does one prop determine another?

Use a discriminated union:

```ts
type: "text" → value: string
type: "number" → value: number
```

### Is it children?

Usually:

```ts
children?: React.ReactNode;
```

or:

```ts
React.PropsWithChildren<Props>
```

### Does it wrap a native HTML element?

Reuse its props:

```ts
React.ComponentProps<"button">
```

# 27. The Big Picture

All of these topics are really teaching one idea:

> **Type the contract of your component accurately.**

```text
                         Component Contract
                                │
             ┌──────────────────┼──────────────────┐
             ↓                  ↓                  ↓
           Values            Callbacks           Children
             │                  │                  │
             ↓                  ↓                  ↓
         string/number       function          ReactNode
         boolean/etc.
             │
             ↓
        ┌────┴─────┐
        ↓          ↓
    required    optional
        │          │
        └────┬─────┘
             ↓
         Variants
             │
             ↓
    ┌────────┴────────┐
    ↓                 ↓
 "link"            "button"
    ↓                 ↓
  href             onClick
```

The progression of this Part 1 is therefore:

```text

       ↓

       ↓

       ↓
```

### One-line revision
