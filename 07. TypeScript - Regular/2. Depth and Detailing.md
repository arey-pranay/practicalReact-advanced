# 1. ReactNode

## What is `ReactNode`?

`ReactNode` represents **anything React can render**.

It can include:

- JSX elements
- strings
- numbers
- `null`
- `undefined`
- booleans
- arrays of renderable nodes
- fragments
- portals

```tsx
import { ReactNode } from "react";

interface ContainerProps {
  title: string;
  children: ReactNode;
}

function Container({ title, children }: ContainerProps) {
  return (
    <div>
      <h2>{title}</h2>
      <div>{children}</div>
    </div>
  );
}
```

Usage:

```tsx
<Container title="Profile">
  Hello
</Container>

<Container title="Profile">
  <button>Click me</button>
</Container>

<Container title="Profile">
  {isLoggedIn && <Dashboard />}
</Container>
```

All of these are valid because they produce renderable React content.

## `ReactNode` vs `JSX.Element`

This distinction is important.

```tsx
let a: React.ReactNode;
let b: JSX.Element;
```

`ReactNode` is much broader.

For example:

```tsx
const value1: React.ReactNode = "Hello";
const value2: React.ReactNode = 42;
const value3: React.ReactNode = null;
const value4: React.ReactNode = <div />;
```

But a `JSX.Element` represents an actual JSX element:

```tsx
const element: JSX.Element = <div />;
```

So:

```tsx
function Component(): JSX.Element {
  return <div>Hello</div>;
}
```

is different from:

```tsx
function Component(): React.ReactNode {
  return "Hello";
}
```

### Mental Model

Think:

```text
JSX.Element
    ↓
one React element

ReactNode
    ↓
anything React knows how to render
```

### Important Gotcha

Don't automatically use `JSX.Element` for `children`.

Usually:

```tsx
children: React.ReactNode;
```

is the better type.

### Revision

> **Use `ReactNode` when a prop can contain anything React can render.**

---

# 2. `PropsWithChildren`

React also provides a utility type for adding `children` to props.

```tsx
import { PropsWithChildren } from "react";

interface CardProps {
  title: string;
}

function Card({ title, children }: PropsWithChildren<CardProps>) {
  return (
    <div>
      <h2>{title}</h2>
      {children}
    </div>
  );
}
```

This is essentially a convenient way of expressing:

```tsx
interface CardProps {
  title: string;
  children?: React.ReactNode;
}
```

### Important Detail

`PropsWithChildren<T>` makes `children` **optional**.

If your component requires children, explicitly write:

```tsx
interface CardProps {
  title: string;
  children: React.ReactNode;
}
```

rather than relying on `PropsWithChildren`.

### Revision

> **`PropsWithChildren<T>` adds an optional `children: ReactNode` prop to `T`.**

---

# 3. Linking Types Between Props

Sometimes props are not independent.

One prop determines what another prop is allowed to contain.

For example:

```tsx
interface DropdownProps<T> {
  options: T[];
  value: T;
  onChange: (value: T) => void;
}
```

Now all three are connected through `T`.

```tsx
function Dropdown<T>({ options, value, onChange }: DropdownProps<T>) {
  // ...
}
```

Suppose:

```tsx
const options = ["React", "Vue", "Angular"];

<Dropdown
  options={options}
  value="React"
  onChange={(value) => {
    // value is string
  }}
/>
```

The same type flows through:

```text
options
   ↓
   T
   ↓
value
   ↓
onChange
```

Without generics, we might accidentally lose this relationship:

```tsx
interface BadDropdownProps {
  options: string[];
  value: string;
  onChange: (value: string) => void;
}
```

This is fine for strings, but the component cannot naturally adapt to:

```tsx
number[]
User[]
Product[]
```

### Generic Version

```tsx
interface DropdownProps<T> {
  options: T[];
  value: T;
  onChange: (value: T) => void;
}
```

Now:

```tsx
Dropdown<number>
Dropdown<string>
Dropdown<User>
```

can all work.

### Mental Model

Generics allow you to say:

> "I don't know the type yet, but whatever type you give me, keep it consistent everywhere."

### Revision

> **Use generics when multiple props need to share the same inferred type.**

---

# 4. Generic Components

A generic React component allows the component to work with many data types while preserving type safety.

```tsx
interface ListProps<T> {
  items: T[];
  renderItem: (item: T) => React.ReactNode;
}

function List<T>({ items, renderItem }: ListProps<T>) {
  return (
    <ul>
      {items.map((item, index) => (
        <li key={index}>
          {renderItem(item)}
        </li>
      ))}
    </ul>
  );
}
```

Usage:

```tsx
const users = [
  { id: 1, name: "Pranay" },
  { id: 2, name: "Rahul" }
];

<List
  items={users}
  renderItem={(user) => (
    <span>{user.name}</span>
  )}
/>
```

TypeScript understands that:

```tsx
user
```

is:

```tsx
{
  id: number;
  name: string;
}
```

So:

```tsx
user.name
```

works.

But:

```tsx
user.age
```

would produce an error.

## Why not `any`?

This:

```tsx
renderItem: (item: any) => React.ReactNode;
```

throws away the main benefit of TypeScript.

With generics:

```tsx
renderItem: (item: T) => React.ReactNode;
```

the component remains reusable **and** type-safe.

### Mental Model

```text
List<T>

items        → T[]
renderItem   → receives T
```

Everything stays connected.

### Revision

> **Generic components let React components work with different data shapes without losing type safety.**

---

# 5. Partial Autocomplete with `Partial<T>`

Suppose we have:

```tsx
type ThemeOptions = {
  primaryColor: string;
  secondaryColor: string;
  borderRadius: number;
};
```

Normally:

```tsx
function updateTheme(options: ThemeOptions) {}
```

requires everything:

```tsx
updateTheme({
  primaryColor: "blue",
  secondaryColor: "white",
  borderRadius: 8
});
```

But sometimes we only want to override a few properties.

Use:

```tsx
function updateTheme(options: Partial<ThemeOptions>) {}
```

Now:

```tsx
updateTheme({
  primaryColor: "blue"
});
```

is valid.

And TypeScript still provides autocomplete:

```text
primaryColor
secondaryColor
borderRadius
```

## What does `Partial<T>` actually do?

Given:

```tsx
type User = {
  name: string;
  age: number;
  email: string;
};
```

This:

```tsx
Partial<User>
```

becomes conceptually:

```tsx
{
  name?: string;
  age?: number;
  email?: string;
}
```

### Revision

> **`Partial<T>` makes every property of `T` optional while preserving their original types.**

# 6. `as const`

`as const` tells TypeScript:

> "Infer the most specific literal types possible, and treat this structure as readonly."

Without it:

```tsx
const roles = ["admin", "editor", "viewer"];
```

TypeScript generally infers:

```tsx
string[]
```

So:

```tsx
type Role = typeof roles[number];
```

becomes:

```tsx
string
```

Not useful.

With:

```tsx
const roles = ["admin", "editor", "viewer"] as const;
```

TypeScript sees:

```tsx
readonly ["admin", "editor", "viewer"]
```

Now:

```tsx
type Role = typeof roles[number];
```

becomes:

```tsx
"admin" | "editor" | "viewer"
```

## Why `[number]`?

This is a very important TypeScript trick.

```tsx
typeof roles
```

gives us the tuple:

```tsx
readonly ["admin", "editor", "viewer"]
```

Then:

```tsx
typeof roles[number]
```

means:

> "Give me the type of any numeric index of this tuple."

Possible values are:

```tsx
"admin"
"editor"
"viewer"
```

Therefore:

```tsx
type Role =
  | "admin"
  | "editor"
  | "viewer";
```

### Runtime vs Type Level

The actual array exists at runtime:

```tsx
const roles = [...]
```

The union only exists at compile time:

```tsx
type Role = typeof roles[number];
```

### Revision

> **`as const` preserves literal values instead of widening them to general types.**

---

# 7. `keyof typeof`

This is one of the most useful TypeScript patterns for configuration objects.

Consider:

```tsx
const STATUS_CODES = {
  SUCCESS: 200,
  NOT_FOUND: 404,
  SERVER_ERROR: 500,
} as const;
```

We can extract the keys:

```tsx
type StatusCodeKey = keyof typeof STATUS_CODES;
```

Result:

```tsx
"SUCCESS" | "NOT_FOUND" | "SERVER_ERROR"
```

We can also extract the values:

```tsx
type StatusCodeValue =
  typeof STATUS_CODES[StatusCodeKey];
```

Result:

```tsx
200 | 404 | 500
```

## Understanding the pieces

### `typeof`

In a type position:

```tsx
typeof STATUS_CODES
```

means:

> "Give me the TypeScript type of this variable."

### `keyof`

```tsx
keyof typeof STATUS_CODES
```

means:

> "Give me the keys of that type."

### Indexed access

```tsx
typeof STATUS_CODES[StatusCodeKey]
```

means:

> "Give me the types of the values at those keys."

### Mental Model

```text
const object
     ↓
typeof object
     ↓
object's type
     ↓
keyof
     ↓
object's keys
```

### Revision

> **`keyof typeof` converts the keys of a runtime object into a compile-time union.**

---

# 8. Conditional Types

Conditional types allow TypeScript to make a type-level decision.

Syntax:

```tsx
T extends U ? X : Y
```

Read it as:

> If `T` extends `U`, use `X`; otherwise use `Y`.

Example:

```tsx
type IsString<T> =
  T extends string ? "Yes" : "No";
```

Now:

```tsx
type A = IsString<string>;
// "Yes"

type B = IsString<number>;
// "No"
```

This happens entirely at compile time.

There is no runtime `if`.

### Runtime conditional

```tsx
if (typeof value === "string") {
  // ...
}
```

### Type-level conditional

```tsx
type IsString<T> =
  T extends string ? "Yes" : "No";
```

These look similar conceptually but operate in completely different worlds.

### Revision

> **Conditional types are compile-time `if/else` logic for types.**

---

# 9. Conditional Types + `infer`

`infer` allows TypeScript to extract part of a type.

Example:

```tsx
type GetArrayElement<T> =
  T extends Array<infer U> ? U : never;
```

Now:

```tsx
type A = GetArrayElement<string[]>;
// string

type B = GetArrayElement<number[]>;
// number
```

The interesting part is:

```tsx
Array<infer U>
```

TypeScript effectively says:

> "If `T` is an array, figure out what its element type is and call it `U`."

This pattern appears heavily in advanced utility types.

### Revision

> **`infer` lets conditional types capture and reuse a type hidden inside another type.**

---

# 10. Type Narrowing

TypeScript can start with a broad type and narrow it based on runtime checks.

Example:

```tsx
function printValue(value: string | number) {
  if (typeof value === "string") {
    value.toUpperCase();
  } else {
    value.toFixed(2);
  }
}
```

Initially:

```tsx
value: string | number
```

Inside:

```tsx
if (typeof value === "string")
```

TypeScript knows:

```tsx
value: string
```

Inside `else`:

```tsx
value: number
```

This is called **type narrowing**.

## Common narrowing techniques

### `typeof`

```tsx
typeof value === "string"
```

### `instanceof`

```tsx
value instanceof Error
```

### Equality checks

```tsx
if (value === null)
```

### Property checks

```tsx
if ("name" in value)
```

### Discriminated unions

```tsx
if (state.status === "success")
```

### Revision

> **Type narrowing reduces a union into a more specific type using runtime information.**

---

# 11. Discriminated Unions

Discriminated unions are extremely useful for React state.

Consider:

```tsx
type State =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: string }
  | { status: "error"; error: Error };
```

The common property:

```tsx
status
```

is the **discriminant**.

Now:

```tsx
function Component({ state }: { state: State }) {
  if (state.status === "success") {
    return <div>{state.data}</div>;
  }

  if (state.status === "error") {
    return <div>{state.error.message}</div>;
  }

  return null;
}
```

TypeScript automatically narrows the state.

When:

```tsx
state.status === "success"
```

TypeScript knows:

```tsx
state.data
```

exists.

But when:

```tsx
state.status === "error"
```

TypeScript knows:

```tsx
state.error
```

exists.

## Why this is better than optional properties

A weaker design would be:

```tsx
type BadState = {
  status: string;
  data?: string;
  error?: Error;
};
```

This technically allows nonsense states:

```tsx
{
  status: "loading",
  data: "Some data",
  error: new Error()
}
```

Our discriminated union prevents that.

Valid states become explicit:

```text
idle
loading
success + data
error + error
```

### React Example

```tsx
type State =
  | { status: "loading" }
  | { status: "success"; users: User[] }
  | { status: "error"; message: string };

function Users({ state }: { state: State }) {
  switch (state.status) {
    case "loading":
      return <Spinner />;

    case "success":
      return <UserList users={state.users} />;

    case "error":
      return <ErrorMessage message={state.message} />;
  }
}
```

### Revision

> **Use discriminated unions when a value can exist in several mutually exclusive states.**

---

# 12. Exhaustive Checking with `never`

Discriminated unions become even more powerful when combined with `never`.

```tsx
function assertNever(value: never): never {
  throw new Error(`Unexpected value: ${value}`);
}
```

Then:

```tsx
function renderState(state: State) {
  switch (state.status) {
    case "loading":
      return <Spinner />;

    case "success":
      return <div>{state.data}</div>;

    case "error":
      return <div>{state.error.message}</div>;

    default:
      return assertNever(state);
  }
}
```

Now suppose we add:

```tsx
| { status: "idle" }
```

to `State`.

TypeScript will tell us that the switch isn't exhaustive.

This is extremely useful because adding a new state forces us to update every relevant code path.

### Revision

> **`never` can make discriminated-union handling exhaustive at compile time.**

---

# 13. Template Literal Types

Template literal types allow us to construct string unions.

```tsx
type Direction = "top" | "bottom";
type Alignment = "left" | "right";

type Placement =
  `${Direction}-${Alignment}`;
```

TypeScript generates:

```tsx
"top-left"
| "top-right"
| "bottom-left"
| "bottom-right"
```

Now:

```tsx
const placement: Placement = "top-left";
```

works.

But:

```tsx
const placement: Placement = "center-left";
```

doesn't.

## React Use Cases

This can be useful for:

- event names
- CSS-like tokens
- component variants
- spacing systems
- responsive breakpoints
- design-system APIs

Example:

```tsx
type Size = "small" | "large";
type Variant = "primary" | "secondary";

type ButtonClass =
  `button-${Variant}-${Size}`;
```

### Revision

> **Template literal types generate precise string unions from other string unions.**

---

# 14. Utility Types: `Pick`

`Pick` creates a type containing only selected properties.

```tsx
interface User {
  id: number;
  name: string;
  email: string;
  age: number;
}
```

We can create:

```tsx
type UserPreview =
  Pick<User, "id" | "name">;
```

Equivalent to:

```tsx
type UserPreview = {
  id: number;
  name: string;
};
```

### React Use Case

A component may only need:

```tsx
<UserCard user={user} />
```

where `UserCard` only cares about:

```tsx
id
name
```

Instead of duplicating the shape manually, use `Pick`.

### Revision

> **`Pick<T, K>` keeps only the selected properties from `T`.**

---

# 15. Utility Types: `Omit`

`Omit` does the opposite.

```tsx
type UserWithoutId =
  Omit<User, "id">;
```

Result:

```tsx
{
  name: string;
  email: string;
  age: number;
}
```

### React Example

Suppose a component internally generates an ID.

```tsx
interface InputProps {
  id: string;
  label: string;
  placeholder?: string;
}
```

We could create:

```tsx
type GeneratedInputProps =
  Omit<InputProps, "id">;
```

Now consumers don't provide `id`.

### Revision

> **`Omit<T, K>` removes selected properties from `T`.**

---

# 16. Utility Type: `Required`

`Required<T>` makes every property required.

```tsx
interface User {
  name: string;
  email?: string;
}
```

Then:

```tsx
type CompleteUser =
  Required<User>;
```

becomes:

```tsx
{
  name: string;
  email: string;
}
```

### Mental Model

```text
Partial<T>   → everything optional
Required<T>  → everything required
Pick<T, K>   → keep selected properties
Omit<T, K>   → remove selected properties
```

### Revision

> **Utility types transform existing types instead of forcing you to rewrite them.**

---

# 17. Polymorphic / Dynamic Props with `as`

Many React design systems support:

```tsx
<Box />
<Box as="section" />
<Box as="button" />
<Box as="a" />
```

The component changes the underlying element.

This is called a **polymorphic component**.

A simplified version:

```tsx
import {
  ElementType,
  ComponentPropsWithoutRef
} from "react";

type BoxProps<T extends ElementType> = {
  as?: T;
  children?: React.ReactNode;
} & ComponentPropsWithoutRef<T>;

function Box<T extends ElementType = "div">(
  { as, children, ...rest }: BoxProps<T>
) {
  const Component = as || "div";

  return (
    <Component {...rest}>
      {children}
    </Component>
  );
}
```

Now:

```tsx
<Box as="button" onClick={() => {}}>
  Click
</Box>
```

gets button-specific props.

And:

```tsx
<Box as="a" href="/about">
  About
</Box>
```

gets anchor-specific props.

The type of `as` determines which props are allowed.

### Mental Model

```text
as = "button"
       ↓
T = "button"
       ↓
ComponentPropsWithoutRef<T>
       ↓
button props
```

### Why this is powerful

Without polymorphic typing:

```tsx
<Box as="button" href="..." />
```

might accidentally be accepted.

With correct typing, TypeScript understands:

> This is a button, so give it button props.

### Revision

> **Polymorphic components use a generic `as` prop to change the rendered element while preserving the correct props.**

---

# 18. `ElementType`

`ElementType` represents a valid React element type.

For example:

```tsx
T extends React.ElementType
```

allows `T` to represent things such as:

```tsx
"div"
"button"
"a"
"section"
```

as well as React components.

That's why:

```tsx
T extends ElementType
```

is commonly used for polymorphic components.

### Revision

> **`ElementType` is useful when a generic represents either an intrinsic HTML element or a React component.**

---

# 19. `ComponentPropsWithoutRef`

React provides utility types for extracting the props of components/elements.

For example:

```tsx
type ButtonProps =
  React.ComponentPropsWithoutRef<"button">;
```

This gives us the normal props accepted by a button.

So instead of manually writing:

```tsx
interface ButtonProps {
  disabled?: boolean;
  onClick?: ...
  type?: ...
}
```

we can reuse React's existing definition.

This becomes particularly powerful with polymorphic components.

### Related Types

```tsx
ComponentProps<T>
ComponentPropsWithRef<T>
ComponentPropsWithoutRef<T>
```

The distinction becomes important when working with `ref`.

### Revision

> **`ComponentPropsWithoutRef<T>` extracts the props of a React element/component while excluding `ref`.**

---

# 20. Combining `Omit` with Component Props

A common pattern in React libraries is:

```tsx
type ButtonProps =
  Omit<
    React.ComponentPropsWithoutRef<"button">,
    "color"
  > & {
    color?: "primary" | "secondary";
  };
```

Why?

Because the native HTML button may already have a prop we want to redefine.

The process is:

```text
native button props
       ↓
remove conflicting prop
       ↓
add our own version
```

This pattern is extremely common in reusable component libraries.

### Revision

> **Use `Omit` when extending native React props but replacing one or more properties with your own API.**

# 21. `Record`

`Record<K, V>` describes an object whose keys are `K` and whose values are `V`.

Example:

```tsx
type Scores = Record<string, number>;
```

Equivalent idea:

```tsx
{
  [key: string]: number;
}
```

Example:

```tsx
const scores: Record<string, number> = {
  pranay: 95,
  rahul: 88,
};
```

But `Record` becomes particularly useful with unions.

```tsx
type Role = "admin" | "editor" | "viewer";

const permissions: Record<Role, boolean> = {
  admin: true,
  editor: true,
  viewer: false,
};
```

Now TypeScript requires all three roles to exist.

### Revision

> **`Record<K, V>` creates an object type where keys are `K` and values are `V`.**

---

# 22. `keyof` as a Type-Safe Object Key

Consider:

```tsx
interface User {
  id: number;
  name: string;
  email: string;
}
```

Then:

```tsx
type UserKey = keyof User;
```

becomes:

```tsx
"id" | "name" | "email"
```

We can now write:

```tsx
function getValue(
  user: User,
  key: keyof User
) {
  return user[key];
}
```

This prevents:

```tsx
getValue(user, "random");
```

because `"random"` isn't a valid key of `User`.

### Revision

> **`keyof T` produces a union of the property names of `T`.**

---

# 23. Indexed Access Types

Suppose:

```tsx
interface User {
  name: string;
  age: number;
}
```

We can retrieve the type of a specific property:

```tsx
type Name = User["name"];
```

Result:

```tsx
string
```

And:

```tsx
type Age = User["age"];
```

Result:

```tsx
number
```

We can combine this with `keyof`:

```tsx
type UserValue = User[keyof User];
```

Result:

```tsx
string | number
```

This is the same fundamental idea used in:

```tsx
typeof ROLES[number]
```

### Revision

> **Indexed access types let you retrieve property types from another type.**

---

# 24. `typeof` in TypeScript

There are two concepts that are easy to confuse.

JavaScript:

```tsx
typeof value
```

is a runtime operator.

TypeScript:

```tsx
type UserType = typeof user;
```

is a type-level operator.

Example:

```tsx
const user = {
  name: "Pranay",
  age: 22,
};
```

Then:

```tsx
type User = typeof user;
```

produces approximately:

```tsx
{
  name: string;
  age: number;
}
```

This is extremely useful when a runtime object should be the source of truth.

### Revision

> **TypeScript's `typeof` can extract the static type of an existing value.**

---

# 25. Literal Type Widening

This is one of the reasons `as const` is useful.

Consider:

```tsx
let role = "admin";
```

TypeScript usually sees:

```tsx
string
```

But:

```tsx
const role = "admin";
```

can preserve:

```tsx
"admin"
```

because a `const` variable cannot be reassigned.

For objects, however:

```tsx
const config = {
  role: "admin"
};
```

the property can still be widened to:

```tsx
{
  role: string;
}
```

Using:

```tsx
const config = {
  role: "admin"
} as const;
```

preserves:

```tsx
{
  readonly role: "admin";
}
```

### Revision

> **Literal widening turns specific values into broader types; `as const` prevents that widening.**

---

# 26. Generic Constraints

Generics can be restricted using `extends`.

Without a constraint:

```tsx
function getId<T>(value: T) {
  return value.id;
}
```

TypeScript complains because `T` could be anything.

We can say:

```tsx
function getId<T extends { id: number }>(value: T) {
  return value.id;
}
```

Now TypeScript knows every valid `T` must contain:

```tsx
id: number
```

Example:

```tsx
getId({
  id: 1,
  name: "Pranay"
});
```

works.

### Important Mental Model

`extends` in a generic does **not** mean class inheritance here.

It means:

> "T must satisfy this constraint."

### Revision

> **Use generic constraints when a generic needs to guarantee the presence of certain properties or capabilities.**

---

# 27. Generic Constraints in React Components

Suppose we want a generic list where every item has an ID.

```tsx
interface ListProps<T extends { id: number }> {
  items: T[];
  renderItem: (item: T) => React.ReactNode;
}
```

Now:

```tsx
function List<T extends { id: number }>({
  items,
  renderItem
}: ListProps<T>) {
  return (
    <ul>
      {items.map(item => (
        <li key={item.id}>
          {renderItem(item)}
        </li>
      ))}
    </ul>
  );
}
```

The component remains generic, but TypeScript guarantees:

```tsx
item.id
```

exists.

This is much better than:

```tsx
key={item.id as any}
```

### Revision

> **Generic constraints let reusable React components require a minimum structure while preserving the rest of the type.**

---

# 28. Function Types in React Props

Callbacks should be typed explicitly.

```tsx
interface ButtonProps {
  onClick: () => void;
}
```

For an event:

```tsx
interface InputProps {
  onChange: (
    event: React.ChangeEvent<HTMLInputElement>
  ) => void;
}
```

This is preferable to:

```tsx
onChange: Function;
```

because `Function` loses useful information.

With the specific event type, TypeScript knows:

```tsx
event.target
event.currentTarget
```

and their appropriate types.

### Common React event types

```tsx
React.MouseEvent<HTMLButtonElement>
React.ChangeEvent<HTMLInputElement>
React.FormEvent<HTMLFormElement>
React.KeyboardEvent<HTMLInputElement>
React.FocusEvent<HTMLInputElement>
```

### Revision

> **Type React callbacks with the specific event or argument type instead of the broad `Function` type.**

---

# 29. `unknown` vs `any`

`any` essentially says:

> "Stop checking this value."

```tsx
let value: any;

value.foo.bar.baz();
```

TypeScript won't protect us.

`unknown` says:

> "I don't know what this is yet. Prove it before using it."

```tsx
let value: unknown;
```

This is not allowed:

```tsx
value.foo;
```

We need to narrow first:

```tsx
if (typeof value === "string") {
  value.toUpperCase();
}
```

### Mental Model

```text
any
↓
trust me

unknown
↓
prove it
```

For external data such as API responses, `unknown` is generally much safer than `any`.

### Revision

> **Use `unknown` when a value's type is unknown; use `any` only when you intentionally want to disable type checking.**

---

# 30. `never`

`never` represents a value that can never occur.

Example:

```tsx
function fail(message: string): never {
  throw new Error(message);
}
```

The function never successfully returns.

`never` is also useful for exhaustive checking:

```tsx
function assertNever(value: never): never {
  throw new Error("Unexpected value");
}
```

It can also appear naturally when TypeScript determines that no possible values remain after narrowing.

### Revision

> **`never` represents impossible values or code paths that cannot successfully return.**

---

# 31. Combining Everything in a React Component

A more realistic example combines several of these concepts.

```tsx
import {
  ReactNode,
  ElementType,
  ComponentPropsWithoutRef
} from "react";

type Variant = "primary" | "secondary";

type ButtonProps<T extends ElementType = "button"> = {
  as?: T;
  variant?: Variant;
  children?: ReactNode;
} & Omit<
  ComponentPropsWithoutRef<T>,
  "children"
>;

function Button<T extends ElementType = "button">({
  as,
  variant = "primary",
  children,
  ...rest
}: ButtonProps<T>) {
  const Component = as || "button";

  return (
    <Component
      data-variant={variant}
      {...rest}
    >
      {children}
    </Component>
  );
}
```

Now:

```tsx
<Button onClick={() => {}}>
  Save
</Button>
```

works as a button.

And:

```tsx
<Button as="a" href="/profile">
  Profile
</Button>
```

works as an anchor.

We have combined:

```text
Generic
   +
ElementType
   +
ComponentPropsWithoutRef
   +
Omit
   +
ReactNode
   +
literal union
   =
polymorphic type-safe React component
```

This is the kind of pattern used in serious React component libraries and design systems.

# 32. The Big Picture: How These Features Connect

The most important thing is not memorizing every utility type independently.

Understand how they work together.

## Runtime value → Type

```tsx
const roles = ["admin", "editor"] as const;

type Role = typeof roles[number];
```

Flow:

```text
runtime value
     ↓
as const
     ↓
literal tuple
     ↓
typeof
     ↓
indexed access
     ↓
union
```

---

## Object → Keys

```tsx
const config = {
  dark: true,
  compact: false
};

type ConfigKey = keyof typeof config;
```

Flow:

```text
object
 ↓
typeof
 ↓
object type
 ↓
keyof
 ↓
"dark" | "compact"
```

---

## Generic → Connected Props

```tsx
interface SelectProps<T> {
  options: T[];
  value: T;
  onChange: (value: T) => void;
}
```

Flow:

```text
T
├── options: T[]
├── value: T
└── onChange: (value: T) => void
```

The generic creates a relationship between the props.

---

## Discriminated Union → Safe State

```tsx
type State =
  | { status: "loading" }
  | { status: "success"; data: User[] }
  | { status: "error"; error: Error };
```

Flow:

```text
status
  ↓
narrow
  ↓
specific state
  ↓
specific properties become available
```

# 35. Final Cheat Sheet

```tsx
// React children
children: React.ReactNode;

// Add optional children
PropsWithChildren<Props>

// Preserve literals
const x = ["a", "b"] as const;

// Create union from array
type X = typeof x[number];

// Get keys
keyof User;

// Get type of runtime value
typeof user;

// Get keys from runtime object
keyof typeof config;

// Get property type
User["name"];

// Make optional
Partial<User>;

// Make required
Required<User>;

// Keep properties
Pick<User, "id" | "name">;

// Remove properties
Omit<User, "id">;

// Typed dictionary
Record<string, number>;

// Conditional type
T extends U ? X : Y;

// Extract a nested type
T extends Something<infer U> ? U : never;

// Generic component
function List<T>(props: ListProps<T>) {}

// Generic constraint
T extends { id: number }

// Tagged state
type State =
  | { status: "loading" }
  | { status: "success"; data: Data }
  | { status: "error"; error: Error };

// Polymorphic component
T extends React.ElementType

// Native props
React.ComponentPropsWithoutRef<T>;

// Impossible state
never;

// Safer unknown value
unknown;
```

# Core Takeaway

The deeper pattern behind advanced TypeScript is:

```text
Runtime values
      ↓
typeof / as const
      ↓
precise types
      ↓
keyof / indexed access
      ↓
connected types
      ↓
generics / conditional types
      ↓
flexible abstractions
      ↓
React components with strong guarantees
```

The real power comes when these features are **composed**, not when they are memorized individually.

For React specifically, the highest-value concepts to master first are:

1. `ReactNode` vs `JSX.Element`
2. `PropsWithChildren`
3. Generics
4. `keyof` / `typeof`
5. `as const`
6. `Partial` / `Pick` / `Omit`
7. Discriminated unions
8. Type narrowing
9. Conditional types
10. `infer`
11. `ElementType`
12. `ComponentPropsWithoutRef`
13. Polymorphic components
14. `never` and exhaustive checking
