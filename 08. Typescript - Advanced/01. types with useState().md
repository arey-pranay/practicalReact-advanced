# TypeScript — Types with `useState()`

`useState` is one of the first places where TypeScript becomes genuinely useful in React.

The main idea is simple:

> **The type of your state should describe every value that state is allowed to hold.**

Usually TypeScript can infer the state type automatically. The important cases are when the **initial value doesn't provide enough information** or when the state intentionally represents **multiple possible states**.

---

## 1. Basic `useState` Type Inference

With a primitive initial value, TypeScript usually knows the type automatically.

```tsx
const [count, setCount] = useState(0);
```

TypeScript infers:

```text
count
  ↓
number

setCount
  ↓
Dispatch<SetStateAction<number>>
```

Therefore:

```tsx
setCount(10);      // ✅
setCount(20);      // ✅
setCount("hello"); // ❌
```

Similarly:

```tsx
const [name, setName] = useState("Pranay");
```

gives:

```text
name → string
setName → accepts string
```

And:

```tsx
const [active, setActive] = useState(false);
```

gives:

```text
active → boolean
```

### Usually, don't explicitly write the type

This:

```tsx
const [count, setCount] = useState<number>(0);
```

is valid, but usually unnecessary.

This is enough:

```tsx
const [count, setCount] = useState(0);
```

because TypeScript already knows `0` is a number.

### Rule

> **If the initial value clearly tells TypeScript the state type, let inference do the work.**

---

# 2. Explicitly Typing `useState`

The generic syntax is:

```tsx
useState<Type>(initialValue)
```

For example:

```tsx
const [count, setCount] = useState<number>(0);
```

```tsx
const [name, setName] = useState<string>("");
```

```tsx
const [isOpen, setIsOpen] = useState<boolean>(false);
```

The generic tells React/TypeScript:

> "This state is of type `Type`."

---

# 3. When Explicit Types Actually Matter

Consider:

```tsx
const [user, setUser] = useState(null);
```

What type should `user` have?

From the initial value alone, TypeScript sees:

```text
user → null
```

But that's probably not what we mean.

We expect:

```text
initially
   ↓
null

later
   ↓
User object
```

So we explicitly describe both possibilities:

```tsx
type User = {
  id: number;
  name: string;
};

const [user, setUser] = useState<User | null>(null);
```

Now:

```text
user
 │
 ├── User
 └── null
```

This is one of the most important `useState` patterns in TypeScript.

---

# 4. Nullable State

A very common React pattern is:

```tsx
const [data, setData] = useState<Data | null>(null);
```

Why?

Because the component often has multiple states:

```text
Before data arrives
        ↓
      null

After data arrives
        ↓
      Data
```

Example:

```tsx
type User = {
  id: number;
  name: string;
};

const [user, setUser] = useState<User | null>(null);
```

Initially:

```tsx
user === null
```

After fetching:

```tsx
setUser({
  id: 1,
  name: "Pranay",
});
```

TypeScript now knows both are valid.

---

# 5. Why the Union Is Important

Without the union:

```tsx
const [user, setUser] = useState<User>(null);
```

TypeScript complains because:

```text
User
≠
null
```

If `null` is a legitimate state, it must be included:

```tsx
useState<User | null>(null)
```

This is a broader TypeScript principle:

> **If a value can genuinely have multiple types, describe that with a union.**

```ts
User | null
```

means:

```text
either User
or null
```

---

# 6. Narrowing Nullable State

Once you have:

```tsx
const [user, setUser] = useState<User | null>(null);
```

TypeScript won't allow:

```tsx
user.name
```

because `user` might still be `null`.

You need to narrow it:

```tsx
if (user) {
  console.log(user.name);
}
```

After the check, TypeScript understands:

```text
inside if
user → User
```

In JSX:

```tsx
return (
  <div>
    {user && <p>{user.name}</p>}
  </div>
);
```

This is called **type narrowing**.

---

# 7. Objects as State

Suppose:

```tsx
type Form = {
  name: string;
  email: string;
};
```

We can write:

```tsx
const [form, setForm] = useState<Form>({
  name: "",
  email: "",
});
```

Now:

```tsx
setForm({
  name: "Pranay",
  email: "test@example.com",
});
```

works.

But:

```tsx
setForm({
  name: 123,
  email: "test@example.com",
});
```

doesn't.

---

# 8. Updating Object State

Remember that React state updates should preserve the other properties.

```tsx
setForm({
  ...form,
  name: "Pranay",
});
```

Or preferably, when the new state depends on the previous state:

```tsx
setForm((prev) => ({
  ...prev,
  name: "Pranay",
}));
```

TypeScript understands that the result must still satisfy `Form`.

```text
Form
├── name: string
└── email: string
```

So accidentally returning an invalid shape gets caught.

---

# 9. Arrays as State

An empty array creates an important TypeScript situation.

Suppose we want:

```tsx
type User = {
  id: number;
  name: string;
};
```

We might write:

```tsx
const [users, setUsers] = useState<User[]>([]);
```

This means:

```text
users
  ↓
array of User
```

Therefore:

```tsx
setUsers([
  {
    id: 1,
    name: "Pranay",
  },
]);
```

is valid.

---

# 10. Why Type the Empty Array?

Consider:

```tsx
const [users, setUsers] = useState([]);
```

The initial value contains no information about what the array will eventually contain.

We know:

```text
initially → []
later → User[]
```

So explicitly tell TypeScript:

```tsx
const [users, setUsers] = useState<User[]>([]);
```

Now the state contract is clear.

This is one of the most useful situations where explicit typing helps.

---

# 11. Arrays of Primitives

The same idea applies to primitive arrays.

```tsx
const [tags, setTags] = useState<string[]>([]);
```

```tsx
const [ids, setIds] = useState<number[]>([]);
```

```tsx
const [selected, setSelected] =
  useState<boolean[]>([]);
```

Equivalent generic syntax:

```tsx
useState<Array<string>>([]);
```

Most React code commonly uses:

```tsx
useState<string[]>([]);
```

because it is concise.

---

# 12. Union Types in State

State can itself have several possible values.

For example:

```tsx
const [status, setStatus] =
  useState<"idle" | "loading" | "success" | "error">(
    "idle"
  );
```

Now only these values are allowed:

```tsx
setStatus("idle");     // ✅
setStatus("loading");  // ✅
setStatus("success");  // ✅
setStatus("error");    // ✅
```

But:

```tsx
setStatus("pending"); // ❌
```

This is much better than:

```tsx
const [status, setStatus] = useState<string>("idle");
```

because `string` is too broad.

---

# 13. State as a Discriminated Union

For more complicated state, you can model the **actual states of the UI**.

For example, an API request:

```ts
type State =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: User }
  | { status: "error"; message: string };
```

Then:

```tsx
const [state, setState] = useState<State>({
  status: "idle",
});
```

Now the state describes the entire state machine:

```text
                 State
                   │
       ┌───────────┼────────────┐
       ↓           ↓            ↓
     idle       loading       success
                                  │
                                  ↓
                                data

                   error
                    │
                    ↓
                 message
```

And TypeScript understands relationships between properties.

```tsx
if (state.status === "success") {
  console.log(state.data);
}
```

Here TypeScript knows that `state` must be:

```ts
{
  status: "success";
  data: User;
}
```

This is much safer than:

```ts
type State = {
  status: string;
  data?: User;
  message?: string;
};
```

because the latter allows invalid combinations.

---

# 14. `useState` with `undefined`

Sometimes the initial state is intentionally undefined.

```tsx
const [user, setUser] =
  useState<User | undefined>(undefined);
```

This means:

```text
user
 ├── User
 └── undefined
```

You can also simply write:

```tsx
const [user, setUser] =
  useState<User>();
```

This results in a state that can initially be `undefined`.

The explicit version:

```tsx
useState<User | undefined>(undefined)
```

can be clearer when reading the code because the possible values are visible.

---

# 15. `null` vs `undefined`

Both can represent "no value", but choose deliberately.

```tsx
useState<User | null>(null)
```

often communicates:

> "There is explicitly no user/data right now."

Whereas:

```tsx
useState<User | undefined>(undefined)
```

often communicates:

> "The value has not been provided/initialized yet."

The important thing isn't that one is universally better.

The important thing is consistency within your application.

---

# 16. Functions as State

This is a slightly more advanced case.

Suppose we want to store a function:

```ts
type Callback = () => void;
```

You might think:

```tsx
const [callback, setCallback] =
  useState<Callback>(() => {});
```

But `useState` treats a function passed to it specially: a function can mean either:

1. the initial value, or
2. a lazy initializer.

Similarly, a function passed to the setter can mean:

1. the new function value, or
2. a functional state updater.

This is why storing functions in state requires more care than normal values.

For most callback/reference use cases, `useRef` or `useCallback` may be more appropriate depending on what you're trying to achieve.

---

# 17. The `SetStateAction` Mental Model

You will sometimes see React's type definitions and wonder about:

```ts
SetStateAction<T>
```

Conceptually:

```ts
type SetStateAction<T> =
  T | ((prevState: T) => T);
```

So when you write:

```tsx
setCount(10);
```

you're giving React:

```text
new value
```

But when you write:

```tsx
setCount((prev) => prev + 1);
```

you're giving React:

```text
function that calculates new value
```

Therefore:

```text
setState
   │
   ├── T
   │
   └── (prev: T) => T
```

This is why both forms are valid.

---

# 18. Why Functional Updates Matter

Suppose:

```tsx
setCount(count + 1);
```

You're calculating the new value using the `count` captured by the current render.

If the new state depends on previous state, the functional form is safer:

```tsx
setCount((prev) => prev + 1);
```

The callback receives the latest state value.

This is particularly important for:

- multiple updates
- batched updates
- asynchronous callbacks
- state transitions based on previous state

### Rule

> **If the next state depends on the previous state, prefer the functional updater.**

---

# 19. Type Inference vs Explicit Generic

A useful decision table:

| Situation | Example | Explicit type? |
|---|---|---|
| Primitive with obvious initial value | `useState(0)` | Usually no |
| String | `useState("")` | Usually no |
| Boolean | `useState(false)` | Usually no |
| Object with initial shape | `useState({ name: "" })` | Often no |
| Empty array | `useState([])` | Usually yes |
| `null` initial value | `useState(null)` | Usually yes |
| `undefined` initial value | `useState<User>()` | Yes |
| Union state | `"idle" \| "loading"` | Yes |
| Complex state machine | discriminated union | Yes |

---

# 20. Common Mistake: `useState(null)`

This is probably the most important beginner mistake.

Bad:

```tsx
const [user, setUser] = useState(null);
```

if you later expect:

```tsx
setUser({
  id: 1,
  name: "Pranay",
});
```

Instead:

```tsx
type User = {
  id: number;
  name: string;
};

const [user, setUser] =
  useState<User | null>(null);
```

The type should describe the **whole lifecycle of the state**, not just its initial value.

---

# 21. Common Mistake: `useState([])`

If the state starts empty:

```tsx
const [users, setUsers] = useState<User[]>([]);
```

Don't rely on an empty array to communicate what will eventually be inside it.

Think:

```text
What does this state represent?

       ↓

An array of User

       ↓

useState<User[]>([])
```

---

# 22. Common Mistake: Using `string` for Variants

Avoid:

```tsx
const [status, setStatus] =
  useState<string>("loading");
```

if only a few values are valid.

Prefer:

```tsx
const [status, setStatus] =
  useState<"idle" | "loading" | "success" | "error">(
    "loading"
  );
```

Now TypeScript becomes useful as a constraint instead of merely saying:

> "This is some string."

---

# 23. Deriving the Type Instead of Guessing

When deciding how to type state, ask:

### What values can this state actually have?

For:

```tsx
const [count, setCount] = useState(0);
```

answer:

```text
number
```

For:

```tsx
const [user, setUser] = useState<User | null>(null);
```

answer:

```text
User | null
```

For:

```tsx
const [users, setUsers] = useState<User[]>([]);
```

answer:

```text
User[]
```

For:

```tsx
const [status, setStatus] =
  useState<"idle" | "loading" | "success">("idle");
```

answer:

```text
" idle "
" loading "
" success "
```

The process is:

```text
What does the state represent?
          ↓
What values can it have?
          ↓
Does the initial value reveal all of them?
          ↓
       Yes ─────→ infer
          │
          No
          ↓
    explicitly type it
```

# 24. `useState` and TypeScript in One Picture

```text
useState<T>(initialValue)
        │
        ├───────────────┐
        ↓               ↓
   current state     setter
        │               │
        │               ├── T
        │               │
        │               └── (prev: T) => T
        │
        ↓
      type T
```

Examples:

```tsx
useState<number>(0)
```

```text
state → number
```

```tsx
useState<User | null>(null)
```

```text
state → User | null
```

```tsx
useState<User[]>([])
```

```text
state → User[]
```

```tsx
useState<"idle" | "loading">("idle")
```

```text
state → "idle" | "loading"
```

# 25. Revision Cheatsheet

### Primitive

```tsx
const [count, setCount] = useState(0);
```

Usually inference is enough.

### Object

```tsx
type User = {
  name: string;
};

const [user, setUser] = useState<User>({
  name: "",
});
```

### Nullable object

```tsx
const [user, setUser] =
  useState<User | null>(null);
```

### Array

```tsx
const [users, setUsers] =
  useState<User[]>([]);
```

### String union

```tsx
const [status, setStatus] =
  useState<"idle" | "loading">("idle");
```

### Functional update

```tsx
setCount((prev) => prev + 1);
```

### Complex state

```tsx
type State =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: User }
  | { status: "error"; message: string };
```

---

# 26. Key Takeaways

1. **Let TypeScript infer obvious state types.**

```tsx
useState(0)
```

2. **Explicitly type state when the initial value doesn't reveal the full type.**

```tsx
useState<User | null>(null)
```

3. **Empty arrays often need an explicit type.**

```tsx
useState<User[]>([])
```

4. **Use unions for genuinely different states.**

```tsx
useState<"idle" | "loading" | "success">("idle")
```

5. **If state has relationships between fields, consider a discriminated union.**

6. **Use functional updates when the next state depends on the previous state.**

```tsx
setCount((prev) => prev + 1);
```

### One-line revision

> **For `useState`, don't type the initial value in isolation—type the complete set of values the state can represent throughout its lifecycle.**
