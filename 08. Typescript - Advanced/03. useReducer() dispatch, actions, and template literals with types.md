# TypeScript + React: `useReducer`, `Reducer`, `Dispatch`, Actions, and Template Literal Types

The easiest way to understand these types is to build a small React reducer and gradually add TypeScript.

The core idea:

- State — the data currently stored.
- Action — a description of what happened.
- Reducer — a function that decides how state changes.
- Dispatch — the function used to send an action to the reducer.
- TypeScript types — ensure that actions and state follow the rules you define.
- Template literal types — let you construct types from strings, useful for naming actions and events.

## 1. First, understand `useReducer`

Imagine building a counter.

With `useState`, you might write:

```
const [count, setCount] = useState(0);

setCount((prev) => prev + 1);
setCount((prev) => prev - 1);
```

This works well for simple state.

But imagine a component with several operations:

- Increment the count.
- Decrement the count.
- Reset it.
- Add a specific amount.
- Set a new value.

You could have several setters, but as the update logic grows, it can become easier to organize the transitions in one place.

That's where `useReducer` helps.

```
const [count, dispatch] = useReducer(reducer, 0);
```

Think of it as:

```
User interaction
      |
      v
   dispatch(action)
      |
      v
     reducer
   (state, action)
      |
      v
  returns new state
      |
      v
 React re-renders
```

The reducer is a regular function. React calls it when an action is dispatched.

## 2. Build a reducer without TypeScript first

A reducer receives two arguments:

```
function reducer(state, action) {
  switch (action.type) {
    case "increment":
      return state + 1;

    case "decrement":
      return state - 1;

    case "reset":
      return 0;

    default:
      return state;
  }
}
```

Its signature is:

```
(state, action) => newState
```

For our counter:

- `state` is a number.
- `action` describes the operation.
- The return value is the next number.

Usage:

```
const [count, dispatch] = useReducer(reducer, 0);

dispatch({ type: "increment" });
dispatch({ type: "decrement" });
dispatch({ type: "reset" });
```

Notice that `dispatch` doesn't directly change the state. It sends an action describing what should happen.

## 3. Define the `Action` type

An action is usually an object with a `type` property.

```
type Action = {
  type: string;
};
```

This says an action has a `type` whose value can be any string.

But that is too permissive.

```
dispatch({ type: "increment" }); // Valid
dispatch({ type: "banana" });    // Also accepted by this type
```

TypeScript cannot distinguish valid operations from invalid ones if `type` is just `string`.

Instead, use a string literal union.

```
type Action = {
  type: "increment" | "decrement" | "reset";
};
```

Now only the listed strings are accepted.

```
dispatch({ type: "increment" }); // Valid
dispatch({ type: "reset" });     // Valid

dispatch({ type: "banana" });    // Type error
```

### Why does this matter?

Your action type documents which operations the reducer supports. It also allows TypeScript to detect misspellings and unsupported actions.

## 4. Type the reducer

Now we know the types of the two arguments and the return value.

```
type State = number;

type Action = {
  type: "increment" | "decrement" | "reset";
};

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case "increment":
      return state + 1;

    case "decrement":
      return state - 1;

    case "reset":
      return 0;

    default:
      return state;
  }
}
```

Let's break down the function signature:

```
function reducer(
  state: State,
  action: Action
): State
```

| Part             | Meaning                                         |
| ---------------- | ----------------------------------------------- |
| `state: State`   | The current state must be a number.             |
| `action: Action` | The action must match the defined action shape. |
| `: State`        | The reducer must return a number.               |

The final `State` is the return type. It is not another argument.

### The general reducer pattern

```
function reducer(state: State, action: Action): State {
  // Decide the next state.
}
```

## 5. What is `Dispatch`?

You will often see this type:

```
React.Dispatch<React.SetStateAction<number>>
```

or:

```
React.Dispatch<Action>
```

They describe different kinds of setters.

### `Dispatch` is a function type

Conceptually, React defines it like this:

```
type Dispatch<A> = (value: A) => void;
```

This is a simplified representation of the relevant type.

It means:

> A function that accepts a value of type `A` and returns nothing meaningful (`void`).

For example:

```
type Action = {
  type: "increment" | "decrement";
};

type MyDispatch = React.Dispatch<Action>;
```

Conceptually, `MyDispatch` behaves like:

```
type MyDispatch = (action: Action) => void;
```

So this is valid:

```
const dispatch: React.Dispatch<Action> = (action) => {
  console.log(action.type);
};

dispatch({ type: "increment" });
```

But this isn't:

```
dispatch({ type: "reset" }); // Type error
```

because `"reset"` is not part of the `Action` type.

### Why does `Dispatch` return `void`?

Calling `dispatch` requests a state update. It does not synchronously return the new state.

You read the updated state through the state value returned by `useReducer`.

## 6. `Dispatch<Action>` vs `Dispatch<SetStateAction<T>>`

These look similar, but they represent different APIs.

### `useState`

```
const [count, setCount] = useState(0);
```

The setter accepts either:

1. A new state value.
2. A function that calculates the next state from the previous state.

Conceptually:

```
type SetStateAction<T> =
  | T
  | ((prevState: T) => T);
```

Therefore:

```
React.Dispatch<React.SetStateAction<number>>
```

is approximately:

```
(value: number | ((prevState: number) => number)) => void
```

Both are valid:

```
setCount(10);
setCount((prev) => prev + 1);
```

### `useReducer`

```
const [count, dispatch] = useReducer(reducer, 0);
```

The dispatch function accepts an action:

```
React.Dispatch<Action>
```

For example:

```
dispatch({ type: "increment" });
dispatch({ type: "reset" });
```

| Type                               | What the function accepts          |
| ---------------------------------- | ---------------------------------- |
| `Dispatch<SetStateAction<number>>` | A number or an updater function    |
| `Dispatch<Action>`                 | An action object matching `Action` |

Remember: `Dispatch` describes the function; the generic argument tells you what that function accepts.

## 7. Actions with additional data: payloads

So far, each action describes an operation without carrying additional information.

What if we want to add a specific amount?

We need a `payload`.

A payload is simply data carried by an action.

```
type Action =
  | { type: "increment" }
  | { type: "decrement" }
  | { type: "add"; payload: number }
  | { type: "reset" };
```

Now the `"add"` action requires a number.

```
dispatch({ type: "add", payload: 5 });
dispatch({ type: "add", payload: 100 });

dispatch({ type: "add" }); // Type error
dispatch({ type: "add", payload: "five" }); // Type error
```

The reducer becomes:

```
function reducer(state: number, action: Action): number {
  switch (action.type) {
    case "increment":
      return state + 1;

    case "decrement":
      return state - 1;

    case "add":
      return state + action.payload;

    case "reset":
      return 0;

    default:
      return state;
  }
}
```

When `action.type === "add"`, TypeScript knows that `action.payload` exists and is a number.

This is called discriminated union narrowing.

## 8. Why use a discriminated union for actions?

Consider this alternative:

```
type Action = {
  type: "increment" | "decrement" | "add" | "reset";
  payload?: number;
};
```

It permits awkward combinations:

```
{ type: "increment", payload: 500 }
{ type: "add" }
{ type: "reset", payload: 10 }
```

All are accepted, even though they might not make sense.

Instead:

```
type Action =
  | { type: "increment" }
  | { type: "decrement" }
  | { type: "add"; payload: number }
  | { type: "reset" };
```

Each action has its own contract.

```
Action
  |
  +-- increment
  |     no payload
  |
  +-- decrement
  |     no payload
  |
  +-- add
  |     payload: number
  |
  +-- reset
        no payload
```

Rule: When different actions require different data, model them as separate object variants in a union.

## 9. TypeScript's `Reducer` utility type

React provides a `Reducer` type, so you don't have to manually write the complete function signature.

You can import the types from React:

```
import { useReducer } from "react";
import type { Reducer, Dispatch } from "react";
```

Then:

```
type State = number;

type Action =
  | { type: "increment" }
  | { type: "decrement" }
  | { type: "add"; payload: number }
  | { type: "reset" };

const reducer: Reducer<State, Action> = (state, action) => {
  switch (action.type) {
    case "increment":
      return state + 1;

    case "decrement":
      return state - 1;

    case "add":
      return state + action.payload;

    case "reset":
      return 0;
  }
};
```

Conceptually, `Reducer<State, Action>` means:

```
type Reducer<State, Action> =
  (prevState: State, action: Action) => State;
```

This is a simplified equivalent of the function contract.

The real React type definitions include additional details, but this mental model is enough for everyday usage.

### Two equally reasonable approaches

Explicitly type the function:

```
function reducer(state: State, action: Action): State {
  // ...
}
```

Or use React's utility type:

```
const reducer: Reducer<State, Action> = (state, action) => {
  // ...
};
```

Both are useful. Pick the style that makes your code clearest.

## 10. Type `useReducer` and `dispatch`

Here's a complete example:

```
import { useReducer } from "react";
import type { Reducer, Dispatch } from "react";

type State = {
  count: number;
};

type Action =
  | { type: "increment" }
  | { type: "decrement" }
  | { type: "add"; payload: number }
  | { type: "reset" };

const reducer: Reducer<State, Action> = (state, action) => {
  switch (action.type) {
    case "increment":
      return { count: state.count + 1 };

    case "decrement":
      return { count: state.count - 1 };

    case "add":
      return { count: state.count + action.payload };

    case "reset":
      return { count: 0 };
  }
};

function Counter() {
  const [state, dispatch] = useReducer(reducer, { count: 0 });

  return (
    <div>
      <p>Count: {state.count}</p>

      <button onClick={() => dispatch({ type: "increment" })}>
        Increment
      </button>

      <button onClick={() => dispatch({ type: "add", payload: 5 })}>
        Add 5
      </button>

      <button onClick={() => dispatch({ type: "reset" })}>
        Reset
      </button>
    </div>
  );
}
```

Notice that we don't need to explicitly annotate `dispatch` in this component. TypeScript infers it from `useReducer`.

Its type is effectively:

```
Dispatch<Action>
```

You can verify the contract by hovering over `dispatch` in your editor.

### Why does `useReducer` infer everything?

Because the reducer already establishes the relationship:

```
Reducer<State, Action>
          |
          +-- state type
          |
          +-- action type
```

React's `useReducer` uses that information to infer the state and dispatch types.

Usually, you only need to define `State`, `Action`, and the reducer correctly.

## 11. Passing `dispatch` to child components

A common real-world use case is passing `dispatch` through props.

```
type Action =
  | { type: "increment" }
  | { type: "reset" };

type CounterControlsProps = {
  dispatch: React.Dispatch<Action>;
};

function CounterControls({ dispatch }: CounterControlsProps) {
  return (
    <>
      <button onClick={() => dispatch({ type: "increment" })}>
        Increment
      </button>

      <button onClick={() => dispatch({ type: "reset" })}>
        Reset
      </button>
    </>
  );
}
```

Parent:

```
function Counter() {
  const [count, dispatch] = useReducer(reducer, 0);

  return (
    <>
      <p>{count}</p>
      <CounterControls dispatch={dispatch} />
    </>
  );
}
```

The child doesn't need to know how state updates work. It only needs to know which actions it is allowed to dispatch.

```
Parent
  |
  +-- owns state and reducer
  |
  +-- passes dispatch
           |
           v
      Child controls
           |
           v
     dispatch(action)
```

This separates the UI that requests an update from the logic that performs the update.

You can also extract the action type to a shared types file when multiple components need it.

# 12. Template literal types

Now let's understand the other topic: template literal types.

JavaScript has template literals:

```
const name = "Pranay";

const message = `Hello, ${name}!`;
```

These create strings at runtime.

TypeScript's template literal types use similar syntax to create types from string patterns.

```
type Greeting = `Hello, ${string}`;
```

This type accepts strings that begin with `"Hello, "`.

```
const a: Greeting = "Hello, Pranay"; // Valid
const b: Greeting = "Hello, World";  // Valid
const c: Greeting = "Goodbye";       // Type error
```

The distinction is important:

```
JavaScript template literal
  → creates a string value

TypeScript template literal type
  → describes which strings are valid
```

## 13. Template literal types for action names

Suppose an application manages users, products, and orders.

You could define action names manually:

```
type ActionType =
  | "user/create"
  | "user/delete"
  | "product/create"
  | "product/delete";
```

But there is a repeated pattern.

Each action combines:

```
resource + "/" + operation
```

Template literal types can express that pattern.

```
type Resource = "user" | "product";
type Operation = "create" | "delete";

type ActionType = `${Resource}/${Operation}`;
```

TypeScript expands this into:

```
type ActionType =
  | "user/create"
  | "user/delete"
  | "product/create"
  | "product/delete";
```

The expansion comes from the cross-product of the union values.

```
Resource       Operation
   |               |
   +---- user -----+---- create → user/create
   |               +---- delete → user/delete
   |
   +-- product ----+---- create → product/create
                   +---- delete → product/delete
```

Usage:

```
const a: ActionType = "user/create";    // Valid
const b: ActionType = "product/delete"; // Valid

const c: ActionType = "user/update";    // Type error
```

This is useful when your strings follow a predictable naming convention.

## 14. Combining template literal types with actions

You can use the same idea to define an action union.

```
type Resource = "user" | "product";
type Operation = "create" | "delete";

type Action = {
  type: `${Resource}/${Operation}`;
};
```

Now these are valid:

```
const a: Action = { type: "user/create" };
const b: Action = { type: "product/delete" };
```

This is rejected:

```
const c: Action = { type: "user/update" };
```

However, this type only validates the action name. If different actions need different payloads, a discriminated union is usually clearer.

For example:

```
type Action =
  | { type: "user/create"; payload: User }
  | { type: "user/delete"; payload: number }
  | { type: "product/create"; payload: Product }
  | { type: "product/delete"; payload: number };
```

Here the action name and payload are tied together.

That relationship is more important than merely limiting the possible strings.

## 15. Template literal types with `keyof`

Template literal types become especially useful with `keyof`.

`keyof` produces a union of an object's property names.

```
type User = {
  id: number;
  name: string;
  email: string;
};

type UserKey = keyof User;
```

The result is:

```
type UserKey = "id" | "name" | "email";
```

Now combine it with a template literal type:

```
type ChangedEvent = `${keyof User}Changed`;
```

TypeScript creates:

```
type ChangedEvent = | "idChanged"
  | "nameChanged"
  | "emailChanged";
```

### Practical example
```
type User = {
  id: number;
  name: string;
  email: string;
};

type ChangedEvent = `${keyof User}Changed`;

function on(event: ChangedEvent) {
  console.log(`Event: ${event}`);
}

on("nameChanged");  // ✅ Valid
on("emailChanged"); // ✅ Valid
on("ageChanged");   // ❌ Error: Invalid event name
```

Key takeaway: Combining keyof with template literal types lets you automatically generate string literal unions from an object's property names, providing type safety without manually listing every possible string.
