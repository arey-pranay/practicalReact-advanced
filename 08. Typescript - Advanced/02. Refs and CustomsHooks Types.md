# TypeScript — Advanced React Types

This section builds on basic TypeScript and focuses on the places where React's types become more interesting:

1. Typing `useRef`
2. Typing returned values of a custom hook
3. Typing complex states
4. Typing complex states — Part 2
5. Tuples with custom hooks

The common idea is:

> **Don't just type individual values. Model the shape and behavior of the data flowing through your React code.**

---

# 1. Typing `useRef`

`useRef` is used to keep a value between renders without causing a re-render when that value changes.

It is commonly used for:

- DOM elements
- timers
- previous values
- mutable instance-like values

The type depends on **what the ref is going to contain**.

---

## 1.1 DOM Refs

Consider:

```tsx
const inputRef = useRef<HTMLInputElement>(null);
```

The type tells TypeScript:

```text
inputRef.current
        ↓
HTMLInputElement | null
```

Why `null`?

Because when the component first renders, the DOM element has not necessarily been attached yet.

So:

```tsx
inputRef.current?.focus();
```

is valid.

And:

```tsx
<input ref={inputRef} />
```

connects the ref to the actual DOM element.

### Mental model

```text
useRef<HTMLInputElement>(null)
             │
             ↓
      "current will eventually
       contain an input element"
             │
             ↓
     initially → null
```

---

# 1.2 Why Do We Need the Generic?

Without a useful type:

```tsx
const inputRef = useRef(null);
```

TypeScript only knows that the initial value is `null`.

It cannot know that you intend to put an HTML input element there.

Therefore:

```tsx
inputRef.current?.focus();
```

may not have the useful type information you expect.

Instead:

```tsx
const inputRef = useRef<HTMLInputElement>(null);
```

Now IntelliSense knows:

```text
inputRef.current.
      ↓
focus()
blur()
select()
value
...
```

---

# 1.3 Different DOM Elements

The generic should match the actual element.

```tsx
const buttonRef =
  useRef<HTMLButtonElement>(null);
```

```tsx
const divRef =
  useRef<HTMLDivElement>(null);
```

```tsx
const formRef =
  useRef<HTMLFormElement>(null);
```

```tsx
const videoRef =
  useRef<HTMLVideoElement>(null);
```

Think:

```text
HTMLInputElement
      ↓
<input>

HTMLButtonElement
      ↓
<button>

HTMLFormElement
      ↓
<form>
```

---

# 1.4 `useRef` for Mutable Values

`useRef` isn't only for DOM elements.

For example:

```tsx
const timerRef = useRef<number | null>(null);
```

Then:

```tsx
timerRef.current = window.setTimeout(() => {
  console.log("done");
}, 1000);
```

Later:

```tsx
if (timerRef.current !== null) {
  clearTimeout(timerRef.current);
}
```

The type describes the complete lifecycle:

```text
timerRef.current
       │
       ├── null
       │
       └── number
```

---

# 1.5 `useRef` vs `useState`

This distinction is important.

### State

```tsx
const [count, setCount] = useState(0);
```

Changing it:

```tsx
setCount(1);
```

causes a re-render.

### Ref

```tsx
const countRef = useRef(0);
```

Changing it:

```tsx
countRef.current = 1;
```

does **not** cause a re-render.

```text
useState
   ↓
value changes
   ↓
React re-renders

useRef
   ↓
.current changes
   ↓
no re-render
```

So don't use `useRef` simply because you want to avoid typing state.

The two hooks have different purposes.

---

# 1.6 Typing `useRef` — Rule

Ask:

> **What will `.current` contain?**

Then use that type.

```tsx
useRef<HTMLInputElement>(null)
```

means:

> `.current` will eventually refer to an input element.

```tsx
useRef<number | null>(null)
```

means:

> `.current` can contain a number or `null`.

```tsx
useRef<User | null>(null)
```

means:

> `.current` can contain a `User` or `null`.

# 2. Typing Returned Values of a Custom Hook

Custom hooks are functions.

Therefore, their return value can be typed just like any other function.

Suppose:

```tsx
function useCounter() {
  const [count, setCount] = useState(0);

  return {
    count,
    increment: () => setCount((prev) => prev + 1),
  };
}
```

TypeScript can infer the return type:

```text
{
  count: number;
  increment: () => void;
}
```

Usually, you don't need to explicitly write it.

---

# 2.1 Explicit Return Type

You can explicitly define it:

```tsx
type CounterResult = {
  count: number;
  increment: () => void;
};

function useCounter(): CounterResult {
  const [count, setCount] = useState(0);

  return {
    count,
    increment: () => setCount((prev) => prev + 1),
  };
}
```

Now the hook has an explicit contract:

```text
useCounter()
    ↓
CounterResult
    │
    ├── count: number
    └── increment: () => void
```

---

# 2.2 When Should We Explicitly Type the Return?

Inference is usually enough:

```tsx
function useCounter() {
  ...
}
```

But an explicit return type can be useful when:

- the hook is part of a reusable library
- the return structure is important
- you want to enforce a public API
- the inferred type becomes complicated
- you want implementation changes to be checked against a fixed contract

For internal/simple hooks:

> **Prefer inference unless an explicit contract provides value.**

---

# 2.3 Custom Hook Returning State

For example:

```tsx
type User = {
  id: number;
  name: string;
};

function useUser() {
  const [user, setUser] =
    useState<User | null>(null);

  return {
    user,
    setUser,
  };
}
```

The returned type is inferred as approximately:

```ts
{
  user: User | null;
  setUser: Dispatch<SetStateAction<User | null>>;
}
```

You don't normally need to manually write that huge type.

This is one of the benefits of TypeScript inference.

# 3. Typing Complex States

Simple state:

```tsx
const [count, setCount] = useState(0);
```

is easy.

The interesting part is when state contains multiple pieces of related information.

For example:

```tsx
type FormState = {
  name: string;
  email: string;
  age: number;
};

const [form, setForm] =
  useState<FormState>({
    name: "",
    email: "",
    age: 0,
  });
```

The type describes the complete state shape.

```text
FormState
├── name: string
├── email: string
└── age: number
```

---

# 3.1 Complex State With Nullable Values

Suppose the state represents a user that may not have loaded yet:

```tsx
type User = {
  id: number;
  name: string;
};

type UserState = {
  user: User | null;
  loading: boolean;
  error: string | null;
};
```

Then:

```tsx
const [state, setState] =
  useState<UserState>({
    user: null,
    loading: false,
    error: null,
  });
```

Now the state describes all three pieces of information.

---

# 3.2 The Problem With Independent State

You could instead write:

```tsx
const [user, setUser] =
  useState<User | null>(null);

const [loading, setLoading] =
  useState(false);

const [error, setError] =
  useState<string | null>(null);
```

This can be perfectly valid.

But as state becomes more interconnected, independent state variables can become harder to reason about.

For example:

```text
loading = false
user = null
error = null
```

Is that valid?

Maybe.

But what about:

```text
loading = true
user = User
error = "Failed"
```

That might be an impossible combination.

This leads to a better approach for complex state:

> **Model the valid states explicitly.**

---

# 4. Complex States Part 2 — Discriminated Unions

Instead of allowing every property combination:

```ts
type State = {
  loading: boolean;
  data?: User;
  error?: string;
};
```

we can model actual states:

```ts
type State =
  | {
      status: "idle";
    }
  | {
      status: "loading";
    }
  | {
      status: "success";
      data: User;
    }
  | {
      status: "error";
      error: string;
    };
```

Now the possibilities are explicit:

```text
              State
                │
       ┌────────┼─────────┐
       ↓        ↓         ↓
     idle    loading    success
                           │
                           ↓
                          data

                         error
                           │
                           ↓
                         error
```

---

# 4.1 Why This Is Better

With the loose version:

```ts
type State = {
  loading: boolean;
  data?: User;
  error?: string;
};
```

all of these are technically possible:

```ts
{
  loading: true,
  data: user,
  error: "Failed"
}
```

But that's probably not a meaningful UI state.

With a discriminated union:

```ts
type State =
  | { status: "loading" }
  | { status: "success"; data: User }
  | { status: "error"; error: string };
```

each state has only the data that makes sense for it.

---

# 4.2 Type Narrowing

The `status` property acts as the discriminator.

```tsx
if (state.status === "success") {
  console.log(state.data);
}
```

TypeScript knows:

```text
state.status === "success"
        ↓
state is
{ status: "success"; data: User }
```

Therefore:

```tsx
state.data
```

is safe.

Similarly:

```tsx
if (state.status === "error") {
  console.log(state.error);
}
```

TypeScript knows `error` exists.

---

# 4.3 Rendering Complex State

This works especially well in React:

```tsx
if (state.status === "loading") {
  return <Spinner />;
}

if (state.status === "error") {
  return <Error message={state.error} />;
}

if (state.status === "success") {
  return <UserCard user={state.data} />;
}

return <EmptyState />;
```

Each branch narrows the type automatically.

# 5. Tuples With Custom Hooks

A custom hook often returns multiple values:

```tsx
function useCounter() {
  const [count, setCount] = useState(0);

  return [count, setCount];
}
```

We expect:

```text
[
  number,
  Dispatch<...>
]
```

But there is an important TypeScript distinction between:

```text
Array
```

and:

```text
Tuple
```

---

# 5.1 Array vs Tuple

An array means:

```ts
string[]
```

> Any number of strings.

A tuple means:

```ts
[string, number]
```

> Exactly two values, where the first is a string and the second is a number.

Compare:

```ts
const arr: (string | number)[] = [
  "hello",
  10,
];
```

versus:

```ts
const tuple: [string, number] = [
  "hello",
  10,
];
```

The tuple preserves the **position and type** of each item.

```text
Array
[string | number, string | number, ...]

Tuple
[0: string, 1: number]
```

---

# 5.2 Why Does This Matter for Custom Hooks?

Consider:

```tsx
function useCounter() {
  const [count, setCount] = useState(0);

  return [count, setCount];
}
```

We want:

```tsx
const [count, setCount] = useCounter();
```

to behave like:

```text
count
  ↓
number

setCount
  ↓
function
```

If TypeScript infers the return as a normal array, it may see something closer to:

```ts
(number | Dispatch<...>)[]
```

Now each position could theoretically contain either type.

That's not what we mean.

We mean:

```text
position 0 → number
position 1 → setter
```

That's a tuple.

---

# 5.3 Explicit Tuple Return Type

We can write:

```tsx
function useCounter():
  [number, React.Dispatch<React.SetStateAction<number>>] {

  const [count, setCount] = useState(0);

  return [count, setCount];
}
```

Now:

```tsx
const [count, setCount] = useCounter();
```

has the correct types.

---

# 5.4 Using `as const`

For simpler custom hooks:

```tsx
function useToggle() {
  const [value, setValue] = useState(false);

  const toggle = () => {
    setValue((prev) => !prev);
  };

  return [value, toggle] as const;
}
```

`as const` tells TypeScript to preserve the returned array as a readonly tuple rather than widening it into a normal array.

Conceptually:

```text
without as const
       ↓
(boolean | function)[]

with as const
       ↓
readonly [
  boolean,
  () => void
]
```

This is a very common pattern for custom hooks.

---

# 5.5 Object Return vs Tuple Return

Custom hooks can return either.

### Object

```tsx
function useCounter() {
  return {
    count,
    increment,
    decrement,
  };
}
```

Usage:

```tsx
const {
  count,
  increment,
  decrement,
} = useCounter();
```

### Tuple

```tsx
function useCounter() {
  return [
    count,
    increment,
    decrement,
  ] as const;
}
```

Usage:

```tsx
const [
  count,
  increment,
  decrement,
] = useCounter();
```

---

# 5.6 Which Should You Use?

### Tuple

Good when:

- there are only a few values
- position is obvious
- you want an API similar to `useState`

Example:

```tsx
const [value, setValue] = useSomething();
```

### Object

Good when:

- there are many returned values
- names make the API clearer
- consumers may need only some values
- positions would become difficult to remember

Example:

```tsx
const {
  data,
  loading,
  error,
  refetch,
} = useUser();
```

### Mental model

```text
Tuple
↓
position has meaning

Object
↓
property name has meaning
```

# 6. Typing a Custom Hook Like `useToggle`

A complete example:

```tsx
function useToggle(
  initialValue = false
): readonly [boolean, () => void] {
  const [value, setValue] =
    useState(initialValue);

  const toggle = () => {
    setValue((prev) => !prev);
  };

  return [value, toggle];
}
```

Usage:

```tsx
const [isOpen, toggle] = useToggle();

toggle();
```

Types:

```text
isOpen
  ↓
boolean

toggle
  ↓
() => void
```

---

# 7. Typing a Generic Custom Hook

Sometimes the hook should work with different types.

For example:

```tsx
function useValue<T>(initialValue: T) {
  const [value, setValue] =
    useState<T>(initialValue);

  return [value, setValue] as const;
}
```

Now:

```tsx
const [name, setName] =
  useValue("Pranay");
```

gives:

```text
name → string
```

And:

```tsx
const [count, setCount] =
  useValue(0);
```

gives:

```text
count → number
```

The generic `T` is inferred from the initial value.

```text
useValue("Pranay")
       ↓
T = string

useValue(0)
       ↓
T = number
```

This is where TypeScript starts becoming more than simple annotations: you're designing **reusable type-safe APIs**.

# 8. How to Decide What Type to Write

When typing React code, don't start by asking:

> "What TypeScript syntax do I need?"

Start with:

> **"What values can exist here, and what relationships do they have?"**

### For `useRef`

Ask:

```text
What will .current contain?
```

Then:

```ts
useRef<HTMLInputElement>(null)
```

or:

```ts
useRef<User | null>(null)
```

---

### For a custom hook

Ask:

```text
What does the hook promise to return?
```

Then decide:

```text
object → { ... }
tuple  → [ ... ]
```

---

### For complex state

Ask:

```text
What are the valid states?
```

If values are independent:

```ts
type State = {
  ...
};
```

If certain values depend on another value:

```ts
type State =
  | { status: "loading" }
  | { status: "success"; data: User }
  | { status: "error"; error: string };
```

---

# 9. Common Mistakes

### Mistake 1 — `useRef(null)` for everything

```tsx
const ref = useRef(null);
```

If it's a DOM ref, tell TypeScript what DOM element it is:

```tsx
const ref = useRef<HTMLInputElement>(null);
```

---

### Mistake 2 — Using state for mutable values that don't affect UI

```tsx
const [timerId, setTimerId] = useState<number | null>(null);
```

If changing the value doesn't need to trigger a render, a ref may be more appropriate:

```tsx
const timerId = useRef<number | null>(null);
```

---

### Mistake 3 — Returning a normal array from a tuple-style hook

```tsx
return [value, toggle];
```

If TypeScript widens it to an array, use:

```tsx
return [value, toggle] as const;
```

or explicitly declare a tuple return type.

---

### Mistake 4 — Making complex state too loose

Avoid:

```ts
type State = {
  status: string;
  data?: User;
  error?: string;
};
```

if there are actually known states.

Prefer:

```ts
type State =
  | { status: "loading" }
  | { status: "success"; data: User }
  | { status: "error"; error: string };
```

# 11. The Big Picture

These five topics are connected:

```text
                 TypeScript + React
                       │
        ┌──────────────┼──────────────┐
        ↓              ↓              ↓
      useRef       Custom Hooks      State
        │              │              │
        ↓              ↓              ↓
   type .current   type return    model states
                       │              │
                       ↓              ↓
                  object / tuple   union types
                       │
                       ↓
                 reusable APIs
```

The progression is:

```text
useRef
  ↓
"What type will current contain?"

Custom hook return
  ↓
"What does this hook promise to return?"

Complex state
  ↓
"What shape does my state have?"

Complex state variants
  ↓
"What states are actually valid?"

Tuples
  ↓
"Does the position of each returned value matter?"
```

### One-line revision

> **Advanced React typing is mainly about modeling contracts: `useRef` types what `.current` contains, custom-hook types describe what a hook returns, complex state types describe valid UI states, and tuples preserve the meaning of each returned position.**
